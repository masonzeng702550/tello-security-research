# 給 Codex 的撰寫 prompt

> 在另一台機器上 `git clone` 本專案後，把下方灰底區塊整段複製給 Codex。
> 底下另附「為什麼這樣寫」的說明，供你自行調整。

---

## 直接複製這段

```
我要寫一篇技術部落格，主題是我對 Ryze Tello 無人機與其 Android App 做的資安研究。
這個 repo 就是研究的完整紀錄。請協助我撰寫。

【第一步：先讀這些，照順序，讀完再動筆】

1. docs/01-prior-art.md
   ★ 最重要。裡面的「新穎性評估」界定了哪些發現是別人早就發表的、
     哪些才是本研究的。寫作時如果搞錯這個，整篇文章會失去可信度。

2. docs/07-blog-outline.md
   撰寫方向。含四幕結構、開場素材、「絕對不要寫的句子」對照表、
   可獨立成篇的支線、標題建議、發表前檢查表。

3. blog-assets/quotes.md
   所有可直接引用的原始數據：封包內容、時間軸、遙測字串、統計數字。
   ★ 引用數據時一律從這裡複製，不要憑記憶重打，也不要自行推算。

4. blog-assets/README.md
   圖片清單與各張的建議用途，以及不可發布的素材。

5. docs/08-research-journey.md
   ★ 研究歷程。動機、環境建置的完整過程、踩過的坑、走錯的路。
     文章的敘事骨架與細節多數來自這份，不要只寫成果。

6. README.md
   18 份 findings 的索引，含層級與嚴重度。需要細節時再去讀個別的
   docs/findings/Fxx-*.md。

【硬性限制，不可違反】

一、新穎性
  L1（控制通道）的問題大多已有前人發表：
    - Alias Robotics RVDP#1208，Tello Wi-Fi 預設無密碼，CVSS 9.4
    - 同儕審查論文《Analysis of Control Channel Cybersecurity of the
      Consumer-Grade UAV by the Example of DJI Tello》
    - 公開技術文章：以 SDK 指令踢掉已連線的手機

  提及這些時必須標註為前人成果。
  ✗ 不可寫「本研究發現 Tello 可被未認證接管」
  ✓ 應寫「我複現了已知的 SDK 劫持，並補上前人未涵蓋的三點」

  真正查無前人研究的是 L3 的 App 層與資料流：F09、F14、F05、F13、F17。

二、未測試的事情要寫「未測試」
  - emergency / rc 對飛行中機體的實際效果 → 從未送出該指令，僅為依官方文件的推論
  - 教室多機情境 → 只有一台機器，未實地驗證
  - 登入後飛行紀錄是否上傳 → 未登入，未觀測到不等於不會上傳
  詳細的「不可寫 vs 應改寫」對照表在 docs/07-blog-outline.md 第四節。

三、數據不可杜撰或推算
  所有數字必須出自 blog-assets/quotes.md 或 docs/findings/。
  找不到出處的數字就不要寫。

【文章要求】

- 語言：繁體中文，台灣用語（設定/螢幕/網路/目前/影片，不是設置/屏幕/網絡/當前/視頻）
- 篇幅：4000–6000 字
- 讀者：對資安有基本概念的技術讀者，不必解釋什麼是 UDP，但要解釋 Tello 的協定細節
- 結構：採用 docs/07-blog-outline.md 的四幕
    第一幕 以為找到大東西
    第二幕 查證，然後打臉自己
    第三幕 轉向 App 層，找到真正沒人做過的
    第四幕 我搞錯的四件事
- 圖片：用 Markdown 語法引用 blog-assets/img/ 下的檔案，附圖說
- 語氣：克制。不要用「震驚」「駭人」「你的無人機正在監視你」這類寫法。
  本研究的說服力來自證據密度與誠實，不是來自聳動。

【產出】

寫成一個 Markdown 檔案：blog-draft.md

寫完後，請對照 docs/07-blog-outline.md 第八節的發表前檢查表逐項自我檢查，
並在檔案最後附上檢查結果，標明哪幾項通過、哪幾項需要我補充。

【開始前】

如果讀完上述文件後，你對「哪些是新發現、哪些是前人成果」還有不確定的地方，
先問我，不要自行猜測。
```

## 為什麼這樣寫

### 為什麼把 `01-prior-art.md` 排在第一

這是整份 prompt 最重要的設計。若 AI 先讀到 findings，會看到一堆 High 和 Critical，
自然寫成「我發現了嚴重漏洞」——而那句話在懂行的讀者面前三十秒就會被戳破。

先讀新穎性評估，才會建立正確的框架。

### 為什麼要求「數據一律從 quotes.md 複製」

像 `pitch:0;roll:1;yaw:8;vgx:0;...` 這種字串，AI 憑記憶重打幾乎必定出錯，
而錯一個字就等於偽造證據。明確禁止推算也很重要——
例如「1,766 → 0」這種數字不可以被「約 1,800」取代。

### 為什麼指定台灣用語

本研究其中一項發現就是「App 的繁中資源 93.4% 是中國用語」。
如果文章本身用簡體詞彙寫，會非常諷刺。

### 為什麼要求自我檢查表

發表前檢查表在 `docs/07-blog-outline.md` 第八節，有七項。
讓 AI 自己對照一次，能攔下大部分的過度宣稱。

### 可以調整的地方

- **篇幅**：4000–6000 字是一篇完整長文。若想先寫短版，改成「2000 字，只寫第一幕與第二幕」
- **支線**：若想拆成系列文，改為「只寫 docs/07-blog-outline.md 第五節的第 N 條支線」
- **語言**：要寫英文版的話，加一句「以英文撰寫，投稿對象為國際資安社群」，
  並提醒它 `docs/06-disclosure-draft.md` 第六節有現成的英文摘要可參考

## 附：若 Codex 寫完後你要自己複查

最快的三個檢查點：

1. 搜尋文章中有沒有「發現」兩字出現在 SDK／控制通道的段落——若有，檢查是否標註了前人
2. 搜尋 `emergency`、`rc`、「墜落」、「教室」——這幾處必須有「未測試」的字樣
3. 隨機抽三個數字，回 `blog-assets/quotes.md` 對一次
