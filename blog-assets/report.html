研究是怎麼走到現在的

最初的目標是找出可被利用的漏洞。找到了一個 Critical，但查證前人研究後發現核心機制早已被發表。研究因此轉向——而轉向後的方向，才是真正查無前人研究的部分。

  1. 先做前人研究盤點開案時即記錄：控制通道的研究「相當充分」，而 Tello App 本體「查無前人研究」。這個預判後來被證實。
  2. 在控制通道找到 Critical7 個 ASCII 字元即可切斷擁有者的影像連線，且只能靠關閉飛機電源恢復。完整量化並取得 pcap 與畫面證據。
  3. 查證新穎性——核心機制已被發表Alias Robotics 的 RVDP#1208（CVSS 9.4）已涵蓋 Wi-Fi 無密碼；同儕審查論文與公開技術文章已涵蓋「以 SDK 指令踢掉已連線的手機」。
  4. 重新定位L1 的貢獻改為「精化已知結論」；主軸移往 App 層與資料流——那正是開案時就定位為缺口的地方。

敘述紀律：本研究不主張發現了「Tello 可被未認證接管」。 該現象已有公開紀錄。以下明確區分「已知」與「本研究的增量」。

前人已發表

  • Tello Wi-Fi 預設無密碼 —— Alias Robotics RVDP#1208，CVSS 9.4
  • SDK 協定無認證、可劫持 —— 同儕審查論文
  • 以 SDK 指令踢掉已連線的手機 —— 公開技術文章
  • Deauth 攻擊使操作者失去控制

本研究的 L1 增量

  • 兩條路徑的安全模型相反：二進位協定具工作階段綁定，SDK 協定完全沒有。前人未作此區分。
  • 設定 WPA2 密碼無法緩解——實測攻擊照舊成立
  • 不可恢復性：47 秒零恢復，僅能關閉電源
  • 精確時序：18 ms 回 ok，影像 4 ms 內中斷

查無前人研究的部分

商業資安公司的 Tello 案例研究明確未涵蓋 App 分析、飛行日誌、第三方 SDK 與遙測。以下七項目前未見對應的公開研究。

一、未揭露的境外資料傳輸，且無法以權限阻止F09

App 啟動時，一個第三方手把 SDK 將裝置廠牌、機型、套件名上報至中國境內的阿里雲。 該第三方在四個版本、中英文兩種語言的隱私政策中，命中數皆為零。

以受控 A/B 實測：位置、相片、影片、儲存空間六項權限全部拒絕時， 該請求照樣送出，且 payload 與全部授予時逐位元組相同—— 因為所送欄位皆可由系統 API 取得，不需要任何危險權限。

使用者既不知道它存在，也無法透過任何系統設定阻止它。

二、客服頁面載入阿里雲監控與 Google AnalyticsF14

點擊 App 內的「獲取技術支持」會開啟 WebView，該頁載入阿里巴巴的前端監控 SDK， 向阿里雲日誌服務送出含持久性使用者識別碼、工作階段 id、螢幕解析度與連線類型的信標。 隱私政策對阿里雲、ARMS 相關字串的命中數為零。

三、隱私政策的揭露落差是對稱的F05

初稿曾誤判「英文版從未提及 Google Analytics」，查證後發現該主張為誤。 修正後反而浮現更完整的模式：

第三方中文政策英文政策
Bugly（騰訊）揭露0 次
BaiduLBS（百度）揭露0 次
Google Analytics0 次揭露
阿里雲 ARMS ／ GameSir0 次0 次

各語言版本只揭露該受眾「預期會看到」的第三方，兩份都不是完整揭露。 另以資源檔量化：App 的繁體中文資源有 316 條字串，其中中國用語佔 93.4%， 12 組對照有 9 組完全只出現中國用語——繁中資源是簡中的機械字元轉換，未做用語在地化。

四、飛行日誌的混淆已完全求解F13

Tello 的飛行日誌以 DJI_LOG_V3 格式存於手機。本研究求解其混淆方式：

plain[i] = cipher[i] ^ cipher[2]
單位元組 XOR，而金鑰就存放在酬載的第 3 個位元組，隨密文一同送出。

全量驗證：解碼後為 0 的位元組達 30.5%（隨機約 0.4%），熵由 7.962 降至 6.356。 並交叉驗證網路封包與落地檔案適用同一規則（3,543/3,543，100%）—— 攻擊者不必等檔案落地，攔到封包即可即時解碼。

求解過程中否證了兩個假設：金鑰由重複串回推、金鑰每型別固定。

五、教學用的 API 就是攻擊用的 APIF18

官方 SDK 文件全文檢索，auth 出現 0 次——零認證是規格本身，不是實作疏漏。 而 Tello EDU 教學所用的 Python（djitellopy）與 Scratch 擴充，走的正是同一套協定。

官方文件同時記載 emergency 為「Stop motors immediately」、rc a b c d 為直接搖桿控制。 本研究已確認 rc 在此韌體中被識別（以對照組設計），但從未送出這些指令。

六、原生程式庫：百度模組已成孤兒F17

九個原生程式庫逐一分析，未發現任何自訂端點。 而百度定位 SDK 的 liblocSDK8a.so 雖仍隨 APK 出貨，其 18 個 JNI 進入點所指向的 com.baidu.* 類別在 1.6.8.0 全數不存在——結構上無人可呼叫。 此為三條獨立證據中最強的一條，且不依賴執行期觀測、不受加殼影響。

七、六版縱向比對與韌體通道F01 · F10

2019–2024 共六個版本的第三方 SDK 演變；DJI 韌體更新通道的完整協定 （API 走 AWS CloudFront，韌體檔走阿里雲 OSS）。

被自己推翻的四項推論

以下推論在提出後被本研究自己的實驗否證。保留這些紀錄，是因為它們界定了其他結論的可信範圍。

  • 「序號恆為 0，所以可注入飛行指令」以滿舵、持續 21.5 秒、飛手未操作的條件實測，飛機零反應。二進位協定另有以來源位址為基礎的工作階段綁定——該機制不在封包內容中，靜態分析看不到。該項嚴重度由 High 下修為 Low。
  • 「設定 Wi-Fi 密碼可阻擋攻擊」首次測試顯示攻擊失效，但該結果為單次，且與機制認知衝突（WPA2 屬連結層）。重測後攻擊完整重現。若止於單次結果，會產出方向完全相反、且會誤導使用者的緩解建議。
  • 「隱私政策從未提及 Google Analytics」查證後為誤——英文版三個版本皆有揭露。修正後反而浮現「揭露落差是對稱的」這個更完整的模式。
  • 「飛行日誌熵值 7.97，接近隨機、無法還原」那只是尚未找到金鑰。找到後熵降至 6.36。高熵只代表「以目前的假設看起來隨機」，不等於強加密。

尚未證實

  • 登入帳號後飛行紀錄是否上傳（目前未登入，未觀測到上傳）
  • 教室多機情境——僅有一台機器，未實地驗證
  • 飛行日誌各欄位的語意對應
  • App 內 signature 的產生方式（加殼阻擋）

待補的查證

  • 精讀控制通道論文全文，確認其涵蓋範圍
  • 查證 DJI DAT 格式的混淆方式是否已有公開文件
  • 查證是否有人分析過 Tello App 的第三方 SDK
  • 確認 RVDP#1208 是否已進入 CVE
