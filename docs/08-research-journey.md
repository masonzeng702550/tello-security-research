> 這份文件記錄**過程**，不是成果。
> 包含當初為什麼選這個題目、環境是怎麼架起來的、
> 以及中途撞了哪些牆——含那些最後證明是我自己搞錯的部分。
>
> 成果請看 `README.md` 的發現索引；本文件是給部落格與回顧用的敘事素材。

## 一、起點：為什麼是 Tello

### 最初的念頭

題目的起點很單純：**我手上有一台無人機，而它是中國製的。**

Ryze Tello 由深圳市睿炽科技（Ryze Tech）發行，DJI 提供技術支援與後端。
市面上關於 DJI 的資安討論不少，但幾乎全部集中在 DJI 自家的主力 App
（GO 4、Pilot）。Tello 作為一個定價一兩千元、大量進入教育現場的子品牌產品，
**它自己那支 App 有沒有人看過？**

這個問題後來成為整個專案的主軸。

### 三個研究問題

開案時定了三條線：

| | 問題 |
|---|---|
| **RQ1** | Tello 系統存在哪些可實際利用的資安弱點？ |
| **RQ2** | App 蒐集哪些資料、回傳到哪些端點、由誰營運、在哪個司法管轄區？實際行為與隱私政策是否一致？ |
| **RQ3** | 2019→2024 之間，第三方 SDK、權限與後端端點如何演變？ |

**RQ2 從一開始就是主軸。** 因為在開案的前人研究盤點裡，
我就查到控制通道（UDP 8889／8890／11111）的研究「相當充分」，
而 App 本體「查無前人研究」。

這個判斷在三個月後被證實——而且是以我不太想要的方式（見第九節）。

### 一個從一開始就在的疑慮

Tello 產品線在 2023–2024 陸續停售。開案時我就問自己：
**如果後端已經關站，這個題目還成立嗎？**

當時寫下的答案是：仍然成立，只是敘事要改成
「已停售產品的資料流遺留風險」——舊 App 還在使用者手機上、
還會嘗試連線、還持有權限。**棄養裝置的長尾風險本身就是個好角度。**

後來實測發現後端全部還活著，這個備案沒用上。

## 二、第一個意外：App 從 Google Play 消失了

準備開始的第一步是下載 APK。結果：

```
play.google.com/store/apps/details?id=com.ryzerobotics.tello
→ 404 / 「找不到您要尋找的項目」
```

英文與繁中介面都一樣。**App 已從 Play 商店下架。**

這件事當下讓我有點慌——沒有官方通路，怎麼確保拿到的樣本沒被動過手腳？
研究的可信度從第一步就會有問題。

### 但後來我發現「下架」的描述不準確

隔天查官網時發現：

```
ryzerobotics.com/tello/downloads  →  仍然提供 APK 下載
CDN: dl-cdn.ryzerobotics.com
```

**廠商本身從未停止散布。** 下架的只是 Play 商店那個通路。

我回頭把 `samples/MANIFEST.md` 裡的敘述改掉了。這是整個專案第一次
「先寫下結論、後來發現不夠精確、回頭修正」——後面還有很多次。

### 為什麼會被下架？一個推測

APK 的中繼資料裡有個東西很可疑：

```
targetSdk : 30  (Android 11)
```

**一支 2024 年 9 月釋出的 App，targetSdk 停在 30。**

Google Play 有 targetSdk 政策，過舊的 App 會被下架。
這很可能就是直接原因。

而 targetSdk 過舊本身**就是一個資安議題**——它會豁免掉 Android 11+
的多項隱私強化：分區儲存、套件可見性、單次授權等等。
換句話說：**這支 App 用一個過時的相容性等級，繞過了新版 Android 的隱私保護。**

## 三、取得樣本：403、TLS 指紋，與來源驗證

### 鏡像站不讓我下載

既然要做縱向比對，就得從第三方鏡像取得舊版。APKMirror 和 APKPure 都有。

用 PowerShell 抓：

```powershell
Invoke-WebRequest -Uri $url -OutFile $out
# → 403 Forbidden
```

第一反應是 User-Agent 被擋，換了幾個瀏覽器 UA——**還是 403**。

後來才想到：擋的不是 UA，是 **TLS 指紋**。
`Invoke-WebRequest` 底層的 .NET HTTP stack 有自己的 TLS ClientHello 特徵，
和真實瀏覽器不同，CDN 的反爬蟲能直接認出來。

解法很簡單，換成 Windows 內建的 `curl.exe`：

```bash
curl.exe -L -o out.apk "$url"
# → 200 OK
```

**這件事的教訓不在技術，在於「換 UA 沒用」時要想到更底層。**

### 六個版本，橫跨 2019–2024

| 版本 | 大小 | 鏡像上架日 |
|---|---|---|
| 1.6.8.0 | 30.15 MB | 2024-09 |
| 1.6.4.0 | 31.15 MB | 2022-09 |
| 1.6.0.1 | 30.96 MB | 2022-03 |
| 1.6.0.0 | 30.94 MB | 2021-01 |
| 1.4.0.0 | 31.0 MB | 2020-01 |
| 1.3.0.0 | 29.8 MB | 2019-02 |

### 來源驗證：這一步不能省

第三方鏡像的樣本不能直接拿來當證據。我做了兩件事：

1. **簽章驗證**——六版全部通過 v1+v2 簽章，且**由同一把金鑰簽發**
2. **與官方檔案比對**——後來拿到官網直接下載的 1.6.8.0，
   與鏡像版本**位元組完全相同**

第二點特別重要。它把「來源可疑的樣本」變成「來源鏈完整的證據」。

> 如果要寫進文章，這段值得強調：
> **資安研究的可信度不是從分析開始的，是從樣本取得那一刻開始的。**

## 四、第一堵牆：89% 的程式碼不見了

解包完第一版 APK，用 `apktool` 拆出 smali，準備開始讀程式碼。

然後我看到這個：

```smali
.method public b()Lokhttp3/OkHttpClient;
    .locals 1
    const/4 v0, 0x0
    return-object v0        ← 只有 return null
    nop
    nop
    ...（約 290 個 nop）
.end method
```

**方法主體被掏空了。** 只剩下 `return null` 加上一大堆填充指令。

### 加殼確認：愛加密

在 `assets/` 找到：

```
ijiami.ajm          熵值 7.991（幾乎是隨機資料 = 加密過）
ijm_lib/*/libexec.so
s.h.e.l.l.* 系列類別
```

**愛加密（Ijiami）**，中國的商業 App 加固方案。

量化之後的數字很難看：

```
com/ryzerobotics 的方法       96.7% 主體被抽取
第三方函式庫                  90–99%
```

也就是說，**這支 App 的程式碼我幾乎讀不到。**

### 但有一件事救了整個專案

殼抽走的是**方法主體**，但 **DEX 的字串池還在**。

這推論出一個很有用的性質：
如果某個字串（例如一個網域名）不在字串池裡，
那就**沒有任何方法引用它**。

這讓「否定性主張」變得可以驗證——
後面 F01「百度已停用」的結論就建立在這個基礎上。

> 加殼把靜態分析的天花板壓得很低，
> 但**它壓不到字串池，也壓不到類別清單**。
> 找出「殼保護不到什麼」，比抱怨「殼保護了什麼」有用得多。

## 五、準備手機：從解鎖到 root，比想像中久

靜態分析撞牆，剩下的路只有動態分析。而動態分析需要一台 root 的實機。

### 為什麼不用模擬器

模擬器最大的問題是**沒有真實的 Wi-Fi 介面**——
而這個研究有一半是關於無人機的 Wi-Fi 通訊。
另外加殼 App 常有模擬器偵測。

所以：實機。用的是 Pixel 6 Pro。

### 步驟一：解鎖 bootloader（會清空手機）

這是整個過程中唯一不可逆的一步：**解鎖 bootloader 會清除裝置上所有資料。**

```
設定 → 關於手機 → 連點版本號 7 次 → 開發者選項
→ 啟用「OEM 解鎖」與「USB 偵錯」
→ fastboot flashing unlock
→ 音量鍵選擇 → 電源鍵確認 → 裝置清空並重開
```

### 步驟二：Windows 的驅動程式問題

接上 fastboot 模式後，`fastboot devices` **回傳空的**。

裝置管理員裡看得到 USB 裝置（PID_4EE0），但狀態是：

```
CM_PROB_FAILED_INSTALL
```

Windows 認得這個裝置，但裝不上驅動。解法：

```powershell
sdkmanager "extras;google;usb_driver"
pnputil /add-driver "<path>\android_winusb.inf" /install
```

**這一步卡了不少時間**，而且網路上大部分教學都直接跳過，
預設你的驅動會自己裝好。

### 步驟三：Magisk

流程是「下載原廠映像 → 取出 boot.img → 用 Magisk patch → 刷回去」。

下載原廠映像時要接受 Google 的條款頁面。

### 步驟四：root 授權失敗，但設定看起來是對的

Magisk 裝好後，執行 `su` 得到：

```
su: request rejected (2000)
```

而 Magisk 的設定裡「超級使用者存取權」明明已經設成「應用程式及 ADB」。

翻了很久才在 Magisk 的 **Superuser 分頁**找到原因：
裡面有一筆 `com.android.shell` 的**既存拒絕政策**。
設定頁的全域選項是對的，但這筆個別政策把它蓋掉了。

把那筆打開，`su` 就通了。

> **診斷規則**（後來寫進實驗日誌）：
> `request rejected` 是**政策拒絕**，不是「使用者沒回應授權對話框」。
> 看到 rejected 就該去翻個別政策，而不是一直重試。

### 步驟五：系統層憑證，給 mitmproxy 用

Android 7 之後，App 預設不信任使用者安裝的 CA。要攔 HTTPS 就得把
mitmproxy 的憑證裝進**系統憑證庫**。

有 root 之後可以用 Magisk 的 tmpfs bind-mount 做到。
檔名要算 `subject_hash_old`，也就是
`MD5(DER(subject))` 取前 4 bytes、小端序、轉成 8 位十六進位再加 `.0`。

### 環境總算就緒

```
Pixel 6 Pro / Android 13
Magisk root
frida-server 17.x
mitmproxy + adb reverse
系統憑證庫已注入 mitmproxy CA
```

**這一整段花掉的時間，比後來任何一項分析都多。**

## 六、第二堵牆：Frida 一掛上去，App 就死

環境好了，開始用 Frida 攔 TLS 準備解 pinning。結果 App 一啟動就崩潰。

### 兩種不同的死法

**第一種**：hook `System.loadLibrary`

```
UnsatisfiedLinkError: libframework-connectivity-jni.so not found
  at ActivityThread.handleBindApplication
```

多載分派被我的 hook 搞亂了。

**第二種**：hook `ClassLoader.loadClass`

```
VerifyError: Verifier rejected class MyApplication
  ... Anonymous-DexFile@2269758449.jar
```

這個更有意思——`Anonymous-DexFile` 說明殼是用
`InMemoryDexClassLoader` 在執行期還原 dex，
而我的 hook 卡在還原流程中間，讓 ART 的驗證器拒絕了還原後的類別。

### 一個我刻意保留的不確定

**我無法區分「這是加殼器的反除錯機制」還是「單純的相容性衝突」。**

看起來像反除錯，但沒有證據。所以 findings 裡我明確寫了這句：

> 本findings**未主張**此為反篡改偵測——
> 無法區分「不相容」與「刻意阻擋」。

### 解法：延遲掛載

觀察 App 的啟動時序：

```
t = 0        frida spawn
t ≈ 1–2 s    殼完成 dex 還原與 Application 建立
t ≈ 4–5 s    App 發出首波網路請求
```

那麼 **t = 2.5 s** 就是一個窗口：殼做完了，請求還沒發。

```javascript
const DELAY_MS = 2500;
setTimeout(installHooks, DELAY_MS);
```

**成功了。** 這個延遲掛載的技巧後來成為整個專案的標準做法。

### 但故事還沒完

到了研究後期（幾週後），連**帶延遲的 spawn 注入也會讓 App 立刻死亡**，
即使腳本內容只有一個空的 `setTimeout`。

最後改成 **attach 到已經啟動的行程**，App 就穩定了。

代價是：**啟動期發生的事情攔不到。** 這直接造成
`AreaCodeTello` 的寫入來源至今未解——它在啟動時就寫好了。

## 七、中途踩的坑（工具層面）

這些單獨看都是小事，但加起來吃掉了大量時間。列出來給後人避雷。

### PowerShell 的反引號，咬了我兩次

在雙引號字串裡寫 Markdown，結果：

```
`files`  →  \x0c + "iles"    （`f 被當成 form-feed）
`0x1051` →  \x00 + "x1051"   （`0 被當成 null）
```

**控制字元被寫進 findings 文件裡了。**

第一次發生後我立了規則：含反引號的字串一律用單引號 here-string `@'...'@`。
**然後我自己違反了那條規則，第二次又中。**

最後加了一道全專案的控制字元掃描當驗收步驟。

### Python 在 Windows 主控台的編碼

```python
print("已完成")
# UnicodeEncodeError: 'charmap' codec can't encode characters
```

Windows 主控台預設 cp950／cp1252，一 print 中文就炸。
更糟的是：**這會讓腳本在最後一步失敗，讓人誤以為前面的工作也沒做成。**

固定加上：

```python
sys.stdout.reconfigure(encoding="utf-8")
```

### Git Bash 的路徑轉換，兩面都會咬

```bash
adb push /tmp/x.sh /data/local/tmp/
# → 目的地被轉成 C:/Program Files/Git/data/local/tmp/

MSYS_NO_PATHCONV=1 adb push /tmp/x.sh /data/local/tmp/
# → 來源 /tmp/x.sh 變成 Windows adb 找不到的路徑
```

正解是：**來源用 Windows 路徑、目的地用 Unix 路徑，並設 `MSYS_NO_PATHCONV=1`。**

### Android 的 shell 算術是 32 位元

這個最陰險：

```sh
$(( 0x7c47cde000 ))
# → 1204674560
# 正確值應為 532318158848
```

**沒有錯誤訊息，就是安靜地給你一個錯的數字。**
我用它去算 `/proc/pid/mem` 的偏移，`dd` 讀到完全錯誤的位置，
產出一堆 0 bytes 的檔案，查了很久才發現。

正解是在 PC 端用 Python 算好，以字面值傳進去。

### `adb shell` 會等所有子行程結束

`nc` 沒有逾時的話，孤兒行程會一直佔著 stdout，
讓整個 `adb shell` 呼叫掛住——**連續兩次把工具卡到逾時**。

正解：手機端 `nohup ... &` 讓 adb 立刻返回，由電腦端自行計時。

一個安慰是：即使卡住，**tcpdump 的資料其實都還在**，事後撈得回來。

### mitmproxy 的 flow 檔顯示 0 bytes

寫入有緩衝，要等行程結束才 flush。
一度以為什麼都沒抓到，**其實流量一直在錄**。

## 八、實體無人機帶來的麻煩

### 找飛機、充電、然後它壞了

專案開始時飛機還得先找出來，找到後在充電。

真正開始飛之後，App 一直報：

```
警告  飛控傳感器異常
ERROR CODE 29
```

要完整做六面 IMU 校準才排除。而第一次我只做到 1/6 就退出了，等於沒校準。

**教訓**：帶著飛控告警做注入測試，飛機不管有什麼異常反應，
都分不清是注入造成的還是感測器本來就壞的。**那樣測了等於白測。**

### 機身過熱自動關機

某次連續測試後，SDK 遙測顯示：

```
templ:88;temph:91
```

**機身溫度 88–91°C**，飛機隨後自動關機保護。

這件事還差點讓我下錯結論——見第九節。

### Android 一直把 Tello 的 Wi-Fi 踢掉

這個問題困擾了整個後期。手機連上無人機的 Wi-Fi 之後，
過一陣子就自己斷線，導致：

- Frida attach 時 App 已經沒網路
- 韌體檢查觸發不了
- 好幾輪測試白做

根因是 **Android 的連線探測**：它偵測到這個 Wi-Fi「沒有網際網路」
（我們的 proxy 是 App 層的，系統層看不到），
就把網路判定為不良並斷開。

解法：

```bash
settings put global captive_portal_mode 0
settings put global captive_portal_detection_enabled 0
settings put global network_avoid_bad_wifi 0
```

還有一個更隱蔽的原因：飛機設了 Wi-Fi 密碼之後，
手機上**同一個 SSID 存在兩組設定檔**（舊的 `open` + 新的 `wpa2-psk`），
Android 可能反覆嘗試那個過時的。移除舊的才穩定。

### 手機能同時連無人機和網路嗎

可以，但不是用 SIM 卡。用的是 USB 隧道：

```
手機 Wi-Fi ────▶ TELLO（無對外網路）
手機 HTTP  ────▶ 127.0.0.1:8080
                      │  adb reverse（走 USB）
                      ▼
              電腦的 mitmproxy ────▶ 網際網路
```

全域 proxy 指向 localhost，`adb reverse` 把它經 USB 轉到電腦。
**手機在無人機的 Wi-Fi 上，同時擁有（HTTP）網路。**

## 九、幾次差點寫錯結論

這一節是整份文件最值得寫進部落格的部分。

### 一、VPN 沒真的關掉，差點毀掉一整輪資料

做地區相關測試時，Surfshark 的 app 顯示已中斷，
但 `SurfsharkWireGuard` 介面還是 Up，對外 IP 仍在鳳凰城。

而 Ryze 自己的伺服器對我們做 IP 地理定位，回傳判定是**英國**。
App 因此拿到**英文版**客服端點。

如果沒發現，我會寫出「台灣使用者會被導向英文客服」這種完全錯誤的結論。

更糟的是回頭檢查時發現：先前一輪擷取的 CloudFront POP 是 `SFO53`（舊金山）——
台灣使用者正常應該打到東京或香港。**那一輪的 VPN 很可能也是開的。**

> **規則**：每輪地區相關測試前，必須先驗證出口 IP，
> **不能只信 VPN app 的 UI**。

### 二、WPA2 的偽陰性，差點產出方向完全相反的建議

測試「設定 Wi-Fi 密碼能不能擋住攻擊」時，第一次的結果是：
**攻擊完全失效。**

如果就這樣寫下去，我會告訴讀者「設個密碼就安全了」。

但這個結果讓我不安，因為它**與機制認知衝突**——
WPA2 是連結層的東西，理論上不該影響 UDP 應用層的處理。

基於這個疑慮重測，**第二次攻擊完整重現**。

同一批遙測顯示當時機身溫度 88–91°C，飛機隨後因高溫自動關機。
研判首次的無回應與熱保護狀態有關。

> **規則**：與既有機制認知相衝突的**單次陰性結果**，
> 在重測確認前不得作為結論。

### 三、母體定義搞錯，差點推翻自己正確的發現

先前記錄「愛加密抽走 89% 的方法主體」。後來我重新量，得到 **39.2%**，
一度判定先前的數字是錯的，準備發更正。

按套件拆開後才發現：

```
com/ryzerobotics 合計      96.7%
第三方函式庫               90–99%
android/support/*          5–7%    ← 殼放過了
全 dex 整體                39.2%
```

**殼有白名單。** 而 `android/support/*` 佔全 dex 近三成方法，
把 96.7% 稀釋成 39.2%。

原本的 89% 是對的，錯的是我新算的那個母體。

> **規則**：質疑一個比例之前，先確認雙方的**母體定義是否一致**。

### 四、把熵當成結論

分析飛行日誌時量到位元組熵 **7.966 / 8.0**，
於是寫下「接近隨機，無法以簡單方法還原」。

**那是錯的。** 只是還沒找到金鑰而已。

後來發現混淆方式是單位元組 XOR，而**金鑰就存在酬載的第 3 個位元組**。
解碼後熵降到 6.356。

> **高熵只代表「以目前的假設看起來像隨機」，不代表強加密。**

### 五、最痛的一次：測錯了路徑

飛行測試中，我送滿舵搖桿封包 21.5 秒，飛機零反應，
據此下修了 F12 的嚴重度。

那個結論本身是對的。**但我測錯了通道。**

我在同一份研究裡分別證明了：
- SDK 通道**沒有**工作階段綁定
- `rc` 指令**存在且被識別**

**卻跑去測已知有綁定的二進位通道。** 浪費了一整輪飛行測試。

> **規則**：同一裝置上存在多條協定路徑時，
> 「在路徑 A 上注入失敗」不能推廣到路徑 B。
> 分別驗證了兩條路徑的性質之後，**必須明確指出結論只適用於哪一條**。

## 十、最後一個轉折：發現自己的 Critical 別人早就發表了

專案後期，我在控制通道找到一個 Critical——
7 個 ASCII 字元即可切斷擁有者的影像連線，且只能靠關閉飛機電源恢復。

完整量化了，有 pcap、有截圖、有時序。

然後我去查前人研究。

```
Alias Robotics, RVDP#1208
  Tello Wi-Fi 預設無密碼，RVSS 10.0 / CVSS 9.4

《Analysis of Control Channel Cybersecurity of the Consumer-Grade UAV
  by the Example of DJI Tello》—— 同儕審查論文

公開技術文章：
  "...letting attackers disconnect connected phones and mark
   themselves as the controller"
```

**核心機制已經被發表過了。**

### 但這反而讓研究更完整

回頭看開案時寫的前人研究盤點，我當時就記下：

> 控制通道 —— 前人成果**相當充分**
> Tello App 本體 —— **查無前人研究**

**我的預判是對的，只是我自己忘了照著走。**

於是把 L1 的貢獻重新定位成「精化已知結論」——
補上前人沒做的三點：兩條路徑的安全模型相反、WPA2 無法緩解、不可恢復性。

然後把主軸移回開案時就標定的缺口：**App 層與資料流**。
那裡有七項查無前人研究的發現，包括那個
「使用者既不知道它存在、也無法用任何權限設定阻止」的境外上報。

## 十一、回頭看

如果重來一次，我會改的三件事：

1. **先查前人研究，而且要查得比開案時更深。**
   我開案時查了，但查得不夠具體——只查到「控制通道研究充分」，
   沒有查到具體是哪幾篇、涵蓋到什麼程度。
   如果一開始就知道 RVDP#1208 的存在，我會更早把重心放在 App 層。

2. **環境建置的時間要抓兩倍。**
   從解鎖 bootloader 到 root 可用，中間卡了驅動、卡了 Magisk 政策、
   卡了系統憑證。這段時間比後來任何一項分析都長。

3. **每一輪測試前先驗證環境狀態。**
   VPN 有沒有真的關、飛機有沒有還連著、溫度是不是正常。
   我有好幾輪資料是在環境不對的情況下收的，事後才發現。

而如果要說這個專案最值得留下的東西——

**不是那 18 份 findings，是那些被自己推翻的推論。**

因為那些才證明了：其他還站著的結論，是真的站得住。
