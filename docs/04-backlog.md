## A. 教育場景：Tello EDU 與 SDK 協定的課堂風險

**為什麼值得做**：F16 證實 SDK 協定（`command` 等純文字指令）不需任何認證。
而 Tello 的 **Python / Scratch 教學支援走的就是這條協定**——
亦即課堂上教的 API 與攻擊者使用的 API 是同一套。

Tello EDU 以 STEM 教具銷售，典型場景為一間教室內多台無人機同時運作，
**每一台都是開放 Wi-Fi**。

### 待驗證的問題

- [ ] 多台 Tello 同時開機時，SSID 是否可區分？學生裝置是否可能連錯機體？
- [ ] 學生 A 能否以課堂所學的 `djitellopy` 連上學生 B 的飛機？
- [ ] Tello EDU 的「編隊模式」（多機連同一個 AP）是否引入額外風險？
      —— 該模式下所有飛機在同一網段，攻擊面與單機不同
- [ ] Scratch 擴充套件（Node.js 橋接）本身的安全性
- [ ] 官方教材是否提及 Wi-Fi 密碼設定？若未提及，等同預設不設防

### 需要的資源

第二台 Tello（目前僅一台）。**這是本方向的前置條件。**

### 預期產出

一個具體且貼近本地情境的威脅場景。
相較於「攻擊者在 100 公尺內」這種抽象敘述，
「同一間教室的兩個學生」更能說明實際影響。

## B. 從記憶體還原加殼後的 DEX

**為什麼值得做**：F03 記載愛加密抽走 89% 的方法主體，
這是目前所有「無法靜態判斷」結論的共同根因。

還原後可直接回答：

- [ ] `mydjiflight` 請求的 `signature` 欄位如何產生（F10 未解）
- [ ] pinning 實際載入哪幾張憑證，驗證失敗時是否 fallback（F04 未解）
- [ ] `AreaCodeTello` 的寫入點與判定來源（F05 未解）
- [ ] 政策語系的選擇邏輯（F05 的核心未決問題）
- [ ] 是否存在其他未觸發的端點呼叫點（F02 的觀測邊界）

### 做法

Frida hook `InMemoryDexClassLoader` / `DexFile` 相關 API，
於殼完成還原後 dump 記憶體中的 dex。
**注意 F03/F08 的教訓**：大範圍 Java hook 會與殼衝突導致崩潰，
需沿用 `unpin-targeted.js` 的延遲掛載策略。
