## ⚠️ 新穎性：核心機制已有前人發表

**本findings所述的攻擊並非首次發現。** 於 2026-08-26 的查證中確認：

| 前人已發表 | 來源 |
|---|---|
| Tello Wi-Fi 預設無密碼 | Alias Robotics **RVDP#1208**（RVSS 10.0／CVSS 9.4） |
| SDK 協定無認證、可劫持 | 同儕審查論文《Analysis of Control Channel Cybersecurity of the Consumer-Grade UAV by the Example of DJI Tello》 |
| **以 SDK 指令踢掉已連線的手機** | 公開技術文章，明載可「disconnect connected phones and mark themselves as the controller」 |

→ **不得宣稱「本研究發現 Tello 可被未認證接管」。**

### 本findings的實際增量

前人多以「Tello 沒有認證」概括。本findings以實測指出該敘述**不完整**：

| 增量 | 內容 | 前人是否涵蓋 |
|---|---|---|
| **兩條路徑的安全模型相反** | App 二進位協定**具**工作階段綁定（F12 實測）；SDK 協定**完全沒有** | ❌ 未作此區分 |
| **WPA2 密碼無法緩解** | 設定密碼後攻擊照舊成立（實測） | ❌ 未測 |
| **不可恢復性** | 47 秒零恢復、App 內重連無效、僅能關閉電源 | ❌ 未見紀錄 |
| 精確時序與量化 | 18 ms 回 `ok`；影像於 4 ms 內中斷；1,766 → 0 | ❌ |

詳見 `docs/01-prior-art.md` 的新穎性評估。

## 摘要

Tello 除了官方 App 使用的私有二進位協定外，另支援**純文字的 SDK 協定**。

實測顯示：**在擁有者的 App 完全正常連線的狀態下**，
自未經認證的來源送出 **7 個 ASCII 字元 `command`**，即造成

1. 飛機於 **18 毫秒**內回覆 `ok`，進入 SDK 模式
2. **擁有者的影像串流立即中斷**（App 畫面全黑、顯示斷線圖示）
3. 飛機開始向攻擊者廣播**明文的完整飛行遙測**

且該影像中斷**只能靠關閉飛機電源恢復**——而飛行中的無人機無法關機。

F15 的 `conn_req` 路徑在已有客戶端連線時會被拒絕。
**SDK 路徑沒有這個限制。**

## 與 F15 的關鍵差異

| | F15 的 `conn_req` 路徑 | **本findings的 SDK 路徑** |
|---|---|---|
| 擁有者未連線時 | ✅ 成功 | （未單獨測試） |
| **擁有者連線中時** | ❌ **被拒** | ✅ **成功** |
| 對擁有者的影響 | 無 | **影像連線中斷** |
| 攻擊酬載 | 11 bytes 二進位 | **7 bytes 純 ASCII** |
| 需要協定知識 | 需理解二進位框架與 CRC | **無**——公開文件的 SDK 指令 |

→ **本findings的攻擊門檻遠低於 F15，且效果更嚴重。**

## 實測

### 條件

| 項目 | 設定 |
|---|---|
| 官方 App | **正常連線中**，影像串流運作，IMU 已校準無告警 |
| 攻擊酬載 | ASCII 字串 `command`（7 bytes），無標頭、無 CRC |
| 來源 | 埠 `45998`，Android 內建 `nc`，未提供任何憑證 |
| 安全限制 | **僅送出查詢類指令**，未送出任何會產生動作的指令 |

### 時間軸

```
t= 10.106 s   我方 45998 → 8889    "command"
t= 10.124 s   飛機 8889  → 45998   "ok"                    ← 18 ms
t= 10.11  s   App 影像串流停止
t= 10.228 s   飛機 8889  → 8890    "pitch:0;roll:1;yaw:8;…"
```

### 對擁有者影像的影響

| 區間 | App 影像封包數 |
|---|---|
| 我方封包前（0–10.1 s） | **1,583** |
| 我方封包後（10.1–20 s） | **3** |

影像串流於 `t=10.11s` 終止——**與我方封包相隔 4 毫秒**。

截圖佐證（`20260825-03-after-sdk-command.png`）：
App 畫面全黑、Wi-Fi 圖示帶斷線斜線、操控元件變暗。
對照測試前的截圖，該畫面原本有即時影像。

> App 的**控制流並未停止**（1,736 個封包，我方封包後仍有 482 個）。
> 亦即 App 仍在送指令，但**收不到影像**——
> 使用者在飛行中會是「操控還在、畫面全黑」的狀態。

### 攻擊者取得的遙測

飛機自 `t=10.23s` 起持續廣播（281 個封包，至 35.4 s）：

```
pitch:0;roll:1;yaw:8;vgx:0;vgy:0;vgz:0;templ:70;temph:73;
tof:10;h:0;bat:85;baro:49.44;time:0;agx:1.00;agy:-27.00;agz:-999.00;
```

| 欄位 | 內容 |
|---|---|
| `pitch` / `roll` / `yaw` | 三軸姿態 |
| `vgx` / `vgy` / `vgz` | 三軸速度 |
| `agx` / `agy` / `agz` | 三軸加速度 |
| `templ` / `temph` | 機體溫度範圍 |
| `tof` / `h` | 測距感測器高度 / 氣壓高度 |
| `bat` | **電量百分比** |
| `baro` | 氣壓計 |

**純文字、無加密、無認證。**

## 恢復性：唯一的恢復方式是關閉飛機電源

攻擊造成的影像中斷**不會自行恢復，也無法由 App 內操作恢復**。

### 實測一：是否自行恢復

```
我方送出 command        t = 12.096 s
最後一個影像封包        t = 12.080 s      ← 相隔 16 毫秒
```

| 區間 | App 影像封包數 |
|---|---|
| 攻擊前（0–12.1 s） | **1,766** |
| 攻擊後 +0 ~ +10 s | **0** |
| 攻擊後 +10 ~ +25 s | **0** |
| 攻擊後 +25 ~ +47 s | **0** |

**47 秒內沒有任何一個影像封包。** 截圖佐證（`20260825-05`）：
畫面全黑、Wi-Fi 圖示維持斷線狀態。

同一期間：

- **App 的控制流持續運作**（2,893 個封包，至 59 s 仍在送）
  → App 不知道自己被切斷，使用者仍以為連線正常
- **飛機持續向攻擊者廣播遙測**（507 個封包）

### 實測二：能否由 App 內恢復

使用者實際嘗試在 App 內重新連線（點選連線狀態、退回連線畫面重按「連接」）：

> **完全無法恢復。**
> 必須**關閉飛機電源再開機**，之後於連線畫面重新連線，影像才會回來。

### 這決定了本findings的實務嚴重度

**飛行中的無人機無法關閉電源。**

若同一機制於飛行途中發生，使用者將面臨：

| 狀態 | 情形 |
|---|---|
| 影像 | **永久中斷**，該次飛行內無法恢復 |
| 控制 | App 仍在送指令（是否仍有效見下方觀測邊界） |
| 可用的恢復手段 | **無**——關機需要接觸機體 |

→ 實際效果為**被迫盲降**：使用者只能憑肉眼目視距離操控降落，
   若無人機已飛出視線範圍，等同失去該機體。

> ⚠️ **本節的飛行中情境為推論。** 上述實測皆在**地面**進行。
> 「飛行中影像同樣不可恢復」是基於相同機制的合理推斷，
> **但本研究未於實際飛行中測試**。

## 進入 SDK 模式後可取得的資訊（TC-L1-11 實測）

以未經認證的連線送出 `command` 後，逐一測試 SDK 查詢指令。

### 支援的查詢

| 指令 | 回應 | 內容 |
|---|---|---|
| `command` | `ok` | 進入 SDK 模式 |
| `battery?` | `92` | 電量百分比 |
| `wifi?` | `90` | Wi-Fi 訊號雜訊比 |
| `speed?` | `100.0` | 速度設定（cm/s） |
| `height?` | `0dm` | 氣壓高度 |
| `temp?` | `76~78C` | 機體溫度範圍 |
| `tof?` | `100mm` | 測距感測器距離 |
| `baro?` | `52.365494` | 氣壓計讀值 |
| `time?` | `0s` | 飛行計時 |

加上自動推送的狀態廣播（三軸姿態／速度／加速度），
**攻擊者可取得完整的即時飛行狀態**。

### 不支援的查詢

| 指令 | 回應 |
|---|---|
| `sn?` | `unknown command: sn?` |
| `sdk?` | `unknown command: sdk?` |

`sn?`（序號）與 `sdk?`（SDK 版本）屬 Tello EDU / SDK 2.0 的指令集，
本機體（韌體 `01.01.0083`）不支援。

> **這一項對隱私評估有利，應如實記錄**：
> 攻擊者**無法取得機體序號**，
> 亦即缺少可用於長期追蹤特定機體的持久性識別碼。
> 可取得的資訊皆為當下狀態，不含裝置身分。

### 附帶觀察：SDK 解譯器對任意輸入皆會回應

初次測試因管線未保住 UDP datagram 邊界，
`sn?` 被拆成 `s`、`n`、`?` 三個封包送出。
飛機對**每一個**片段都回覆 `unknown command: <字元>`。

→ 說明 SDK 解譯器**無條件處理任何抵達 8889 的文字輸入**，
   不做長度、格式或來源的前置檢查。
   這也提供了一個免費的存在性探測——
   任意字串都會得到回應，可用於確認範圍內是否有 Tello 存在。

## 影響評估

### 已實測

- 未經認證即可**切斷擁有者的影像連線**
- 未經認證即可**取得完整即時飛行遙測**
- 攻擊酬載為 7 個 ASCII 字元，**不需要任何協定逆向知識**
- 在**擁有者正在使用**的狀態下成立

### 推論（**未實測**，見觀測邊界）

進入 SDK 模式後，Tello 的公開 SDK 指令集包含：

| 指令 | 效果 |
|---|---|
| `takeoff` / `land` | 起飛 / 降落 |
| `rc a b c d` | **直接搖桿控制**，四軸值以純文字表示 |
| `emergency` | **立即停止所有馬達** |

若這些指令在同樣條件下可執行，則**飛行中劫持與強制墜落成立**。

### `rc` 指令已確認存在（TC-L1-12，2026-08-25）

上表中的 `rc a b c d`（直接搖桿控制）**已以對照組設計確認為有效指令**。

```
t= 9.11s   送出 'command'       → 回應 'ok'
t=13.20s   送出 'rc 0 0 0 0'    → 無回應、無錯誤
t=17.25s   送出 'rc?'           → 回應 'unknown command: rc?'   ← 對照組
t=21.35s   送出 'rc 0 0 0 0'    → 無回應、無錯誤
```

**對照組是本測試的關鍵。** `rc?` 為刻意構造的無效指令，
飛機回覆 `unknown command`，證明錯誤回報機制正常運作。
而 `rc 0 0 0 0` **未觸發該錯誤**。

依 Tello SDK 規格，`rc` 為高頻控制指令，**設計上即不回應**。
故「無回應且無錯誤」正是指令被接受的表現。

→ **直接搖桿控制指令存在於本韌體，且來自未經認證的來源時不被拒絕。**

測試安全性：送出的是四軸全中位（等同不操作），
且飛機在地面未解鎖（未送 `takeoff`），馬達全程無動作。
**未送出 `takeoff`、`land` 或 `emergency`。**

> ⚠️ **仍未測試的是「`rc` 是否真的驅動飛行中的飛機」。**
> 本測試只證明指令被識別與接受，
> 未證明其對飛行中機體的實際效果。該問題須由階段二回答。

> ⚠️ **本研究未測試 `takeoff`、`land`、`emergency`。**
> 它們會使飛機產生實際動作或墜落，
> 依 `docs/03-ethics-legal.md` 須在空曠場地、備妥防護、
> 並依 `docs/procedures/TC-L1-03-injection-field-test.md` 的程序執行。
> **在測試完成前，不得宣稱「攻擊者可使飛機墜落」。**

## 緩解措施實測：設定 Wi-Fi 密碼**無效**

Tello 官方支援設定 Wi-Fi 密碼，且**廠商自己的字串載明預設無密碼**：

`lib:1.6.8.0:res/values/strings.xml`

> `forgot_password_tips`
> "The aircraft's Wi-Fi network **has no password by default**.
> If you set a password and forget it, press and hold the power button
> for 5 seconds when the aircraft is powered on to restore default settings."

繁中版同義：「飛行器**默認無密碼**；忘記密碼時，可在開機後長按開機鍵 5 秒重置密碼」

→ **「Wi-Fi 無密碼」不再只是本研究單一機體的觀測，而是廠商文件確認的預設值。**

### 測試設計

由 App 設定 Wi-Fi 密碼後，確認網路確實變更：

| | 設定前 | 設定後 |
|---|---|---|
| `cmd wifi list-networks` | `TELLO-XXXXXX  open` | `TELLO-XXXXXX  wpa2-psk` / `wpa3-sae` |

手機以密碼合法連上該網路後，自陌生來源埠重送 `command`。

> 研究者**未取得該密碼**——手機由使用者輸入並連線，
> 測試經由 `adb` 在該手機上執行。此設計使測試不需接觸憑證。

### 結果：攻擊完全照舊

```
t=10.107 s   我方 command（來源埠 57590）
t=10.120 s   飛機回 "ok" + 0xcc 封包        ← 13 毫秒
t=10.276 s   SDK 狀態廣播開始（431 個封包）

App 影像：  我方封包前 1,499 個 → 後 6 個 → 0 個
```

與開放網路下的結果（F16 本文，18 毫秒）**無實質差異**。

### 判讀：密碼是單層且僅限入網的防線

WPA2 保護的是**連結層**——它阻止外人加入網路。
但**一旦進入網路，協定層依然完全沒有認證**。

實務意義：

| 情境 | 密碼是否有效 |
|---|---|
| 陌生人在訊號範圍內，未取得密碼 | ✅ 擋得住 |
| 密碼曾經分享過（教學、借用、多人共飛） | ❌ **完全無效** |
| WPA2 交握被側錄後離線破解 | ❌ 無效 |
| 已在網路內的任何裝置 | ❌ 無效 |

→ **設定 Wi-Fi 密碼是目前唯一可用的緩解措施，但它是單層的、且是共用密鑰。**
   任何一次密碼外流即等同永久失去全部保護，
   因為協定層沒有第二道防線。

### ⚠️ 一個差點成為錯誤結論的偽陰性

**首次**在 WPA2 網路下的測試，飛機**完全無回應**
（0 個回覆封包、0 個 8890 廣播），一度指向「密碼可阻擋攻擊」。

該結果為 **n=1**，且與機制不符——
WPA2 運作於連結層，理論上不影響 UDP 應用層的處理。
基於此疑慮進行重測，第二次即完整重現攻擊。

同一批遙測顯示當時機身溫度為 `templ:88;temph:91`，
飛機隨後因高溫自動關機。**研判首次的無回應與機體熱保護狀態有關**，
但此為推測，未進一步驗證。

> **方法論教訓**：與既有機制認知相衝突的**單次陰性結果**，
> 在重測確認前不得作為結論。
> 本次若止於 n=1，將產出一個方向完全相反、且會誤導使用者的緩解建議。

## 尚未接起來的一步：SDK `rc` 在飛行中的實際效果

本findings與 **F12** 已分別證明兩件事，但**從未將兩者接起來測試**：

```
F16（本findings）  "command" 在 App 連線中送出 → 18 ms 回 ok        ✅ 已證實
                   → SDK 通道無工作階段綁定

TC-L1-12           "rc 0 0 0 0" 被識別，不回 unknown command        ✅ 已證實
                   → 直接搖桿控制指令存在

                            ↓
             "rc" 在飛行中是否真的操控飛機？                        ❌ 未測試
```

### 一項測試設計失誤的記錄

TC-L1-03 階段二（見 **F12**）送出的是**二進位 `0x0050` 搖桿封包**，
結果為零反應，並據此確認二進位協定具工作階段綁定。

**但那條路徑本來就不是本findings所揭露的那條。**
本findings已證明 SDK 通道**沒有**綁定——
階段二卻去測了已知有綁定的二進位通道。

> **教訓**：同一裝置上存在多條協定路徑時，
> 「在路徑 A 上注入失敗」不能推廣到路徑 B。
> 分別驗證了兩條路徑的性質之後，**必須明確指出結論只適用於哪一條**，
> 否則很容易在後續測試中選錯目標。
> 本研究即因此浪費了一整輪飛行測試。

### 明日測試設計（TC-L1-15）

| 步驟 | 動作 | 預期 |
|---|---|---|
| 1 | 飛手起飛、低空懸停、手離開搖桿 | — |
| 2 | 送 `command` | 飛手影像全黑（已知行為，非故障） |
| 3 | 送 `rc 0 0 0 50`（yaw 右轉 50%）持續數秒 | **觀察飛機是否旋轉** |
| 4 | 送 `rc 0 0 0 0` | 回中位 |
| 5 | 飛手降落 | — |

**安全性**：本findings的實測顯示，`command` 送出後
**App 的控制流仍持續運作（49–51 Hz）**，飛手未失去控制權。
代價是飛行中無畫面，故須低空、近距離、目視可及。

**若步驟 3 觀察到旋轉**，則本findings的嚴重度由
「阻斷服務 ＋ 資料外洩」升級為**完整的未授權飛行控制**。

### 更進一步：閒置機體的完整接管（TC-L1-16）

飛機開機但**無任何客戶端連線**時，
以 `command` → `takeoff` → `rc` → `land` 全程接管。

**風險最高**——機體完全由攻擊端控制，飛手僅能以關閉電源中止。
須空曠場地、備妥防護，且應在 TC-L1-15 成立後才進行。

## 攻擊前提

與 F12／F15 相同——攻擊者需位於 Tello 的 Wi-Fi 網段內。
而該網路實測為 **`open`（無密碼）**，門檻為零。
