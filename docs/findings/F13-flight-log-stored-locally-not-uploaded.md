## 待檢驗的假設

`02-threat-model.md` 指出本專案最核心的風險路徑：

> 飛行時手機連在無人機 Wi-Fi（無對外網路）→ 資料暫存於本機
> → 使用者之後切回有網路的 Wi-Fi → **此時才上傳**

F12 已證實飛行期間對外流量為零，但那**不足以排除外傳**——
正因為當時根本沒有對外網路。真正要測的是「恢復網路之後」。

## 前半段成立：飛行紀錄確實存在本機

飛行結束後檢視 App 儲存空間：

`file:/sdcard/Android/data/com.ryzerobotics.tello/files/droneLog/`

```
1786984752121.DAT       256      2026-08-18 00:39
1786984752173.DAT   1611611      2026-08-18 00:45
1786985173439.DAT    123313      2026-08-18 00:46
…
1786986916074.DAT   3302838      2026-08-18 01:24   ← 本次飛行
```

共 16 個檔案、約 8.7 MB。檔名為 epoch 毫秒時間戳。

### 檔案格式：DJI_LOG_V3

取本次飛行的檔案（3.3 MB）檢視：

```
offset 0x00  27000000 03000000 2a000000 00000000
             "BUILD May  7 2019 12:02:11"        ← 飛機韌體建置時間
可見字串:    DJI_LOG_V3                          ← DJI 標準飛行日誌格式 v3
```

**這是 DJI 的標準飛行日誌格式。**

### 與 F12 的 `0x1051` 封包互相印證

F12 觀測到遙測方向有 1,172 個 `0x1051` 封包，
酬載含大量單一位元組長串重複（`636363…`、`525252…`、`a2a2a2…`），
當時**研判**為飛行日誌的 XOR 混淆。

本findings取得的 `.DAT` 檔呈現**完全相同的特徵**
（`UUUU…`、`rrrr…`、`EEEE…`、`QQQQ…`）。

→ 整條鏈確立：

```
飛機 ──0x1051 UDP 封包──▶ App ──寫檔──▶ droneLog/*.DAT (DJI_LOG_V3)
```

F12 中「研判為飛行日誌」的推論，**於本findings升級為確證**。

## 後半段未成立：未觀測到上傳

### 測試條件

| 項目 | 設定 |
|---|---|
| 網路 | 已切回家用 Wi-Fi（有對外網路） |
| 出口 IP | 台灣（VPN 已確認關閉） |

| 觀測時長 | 5 分鐘 |

### 結果

```
連續監測 20 次（每 15 秒），對外連線數：全部為 0

HTTP 交易總計 1 筆：
  connectivitycheck.gstatic.com    1 筆   上行 0 bytes   ← Android 系統
  
夾帶大量上行資料的請求：無
```

**Tello App 在此 5 分鐘內未發出任何網路請求，未上傳任何飛行紀錄。**

## 判讀

在**本次測試條件下**，時間差上傳假設**未獲支持**。
飛行紀錄被蒐集並存於本機，但未自動外傳。

這對研究的意義是雙向的：

- 對 RQ2 而言，這是一個**有利於廠商**的觀測，應如實記錄
- 但它同時提高了 F12 的相對重要性——
  資料留在本機，代表**取得裝置的一方**（或 L2 層的其他 App）
  才是這批飛行紀錄的主要風險來源

## 追加：飛行日誌亦可被外部未認證讀取（2026-08-25）

本findings的結論是「飛行紀錄留在本機、未觀測到上傳」，
容易被讀成「因此風險有限」。**F15 顯示並非如此。**

以未經任何認證的連線直接向飛機索取，飛機會**主動推送飛行日誌資料流**
（`0x1050` LOG_HEADER，含與本findings `.DAT` 檔完全相同的
`BUILD May  7 2019 12:02:11` 字串）。

→ 飛行紀錄的風險不在「App 會不會上傳」，
   而在**任何位於 Wi-Fi 範圍內的人都能直接向飛機索取**。

## 追加：記錄框架已解出，欄位語意未解（2026-08-25）

F13 與 F15 都留著同一個缺口——知道飛行日誌被蒐集、也能被無認證取走，
但**不知道裡面記了什麼**。「攻擊者可取得飛行紀錄」的嚴重度，
取決於裡面是完整飛行軌跡還是只有電池電壓。

### 已確立：記錄框架

以本次飛行的 `1786986916074.DAT`（3.3 MB）分析：

```
檔頭 0x0000  27000000 03000000 2a000000 00000000
             "BUILD May  7 2019 12:02:11"
     0x00f2  "DJI_LOG_V3"

記錄框架  0x55 | 長度(1) | 0x00 | 型別(1) | 酬載…
起始 offset 1256
```

解析結果：

| 項目 | 數值 |
|---|---|
| 記錄總數 | **60,115** |
| 檔案涵蓋率 | **100%** |
| 重新同步次數 | 168 |
| 相異型別 | **58 種** |
| 飛行時長 | 約 4 分鐘 → **每秒約 250 筆** |

**型別與長度高度一致**（`0x8b` 全為 34 bytes、`0x32` 全為 49 bytes、
`0x7a` 全為 28 bytes…）。隨機誤判不會產生這種一對一對應，
故框架的正確性可以確認。

前六大型別：

```
0x8b  7,902 筆 / 34 B      0xe1  5,366 筆 / 92 B
0x32  7,857 筆 / 49 B      0x37  5,363 筆 / 16 B
0x7a  6,617 筆 / 28 B      0xcf  5,358 筆 / 132 B
```

### 未解出：欄位語意

酬載經過擾亂。**已檢驗並否證**最簡單的假設：

> 假設：每筆記錄以單一位元組 XOR，該位元組可由酬載中的長串重複回推
> （零值區 XOR 金鑰會產生重複串）。

檢驗結果：型別 `0x8b`、`0x32`、`0x37` **根本沒有足夠長的重複串**；
型別 `0x7a` 雖有，但回推出的金鑰在各記錄間**不一致**
（前三名候選各只出現 5–6 次 / 400 筆），
且以最常見金鑰解出的 float32 為 `-1.0057e+34` 這類無意義數值。

→ **單位元組 XOR 假設否證。** DJI DAT v3 使用的應是依型別索引的多位元組金鑰表，
   完整還原需要另行投入。

### 對嚴重度判斷的意義

- **可以說的**：飛行日誌是**結構化、高密度**的記錄
  （每秒約 250 筆、58 種型別），且格式為 DJI 的標準 `DJI_LOG_V3`
- **不能說的**：不能宣稱裡面有哪些具體欄位，**本研究尚未解出**
- 擾亂**不是密碼學保護**（無金鑰交換、無認證標籤），
  但本研究**未驗證**公開的 DAT 解析工具是否適用於 Tello 的日誌，
  故也不宜斷言「任何人都能輕易解讀」

## ⚠️ 觀測邊界（本findings的結論很脆弱，務必連同邊界一起引用）

本findings**只能**支持「在下列條件下未觀測到上傳」，
**不能**推論成「App 不會上傳飛行紀錄」：

1. **未登入帳號**。F10 觀測到 DJI 後端請求的 `token` 為空。
   上傳很可能需要帳號，而本測試從未登入。**這是最大的缺口。**
2. **僅觀測 5 分鐘**。批次上傳可能以小時或日為週期。
3. **App 停留在哪個畫面未控制**。上傳可能由特定操作觸發
   （例如進入「飛行紀錄」頁面、或手動同步）。
4. **未測試 App 置於背景或裝置閒置時**的行為。
5. 僅一次飛行、一台裝置、一個版本。
6. 本次飛行全程有 `ERROR CODE 29` 感測器告警，
   不排除異常狀態下的紀錄處理與正常情形有別。
