# F12 — App 原生控制協定：飛行指令明文、序號恆為 0、無防重放

| 欄位 | 內容 |
|---|---|
| 編號 | F12 |
| 層級 | L1 近場 Wi-Fi |
| 分類 | 認證缺失 |
| 嚴重度 | **High** |
| 受影響版本 | 1.6.8.0（韌體 01.01.0083） |
| 狀態 | **T2 — 執行期已觀測**；**注入已於飛行中實測，未觀測到效果**（見下） |
| 對應測試 | TC-L1-08（新增），延伸自 TC-L1-06 |
| 證據 | `pcap:TC-L1-08_flight_20260818-0120.pcap`（46,402 封包 / 239.5 秒 / 實際飛行） |
| 工具 | `tools/decode_tello_proto.py` |

## 摘要

F06 測的是 **Tello SDK 的文字協定**（送 `command`、`takeoff` 等字串）。
但官方 App 實際使用的是**另一套私有二進位協定**——同樣走 UDP 8889，
內容完全不同。

本findings以一次實際飛行的完整封包擷取，證明：
**App 用來操控飛機的搖桿指令封包，序號恆為 0，無任何防重放或認證機制。**

## 三條通道

一次 239.5 秒的實際飛行，共擷取 46,402 個封包：

| 方向 | 埠 | 封包數 | 用途 |
|---|---|---|---|
| 飛機 → 手機 | `62512 → 7777` | 29,525 | 影像串流（H.264 明文） |
| 手機 → 飛機 | `6525 → 8889` | 12,026 | **控制指令** |
| 飛機 → 手機 | `8889 → 6525` | 4,823 | 遙測與飛行日誌 |

## 封包結構

所有封包以 `0xcc` 起始（F06 當時觀測到的那個「不明二進位封包」即是此協定）：

```
cc b000 7f 60 5000 0000 042000290d0114258700 b956
│  │    │  │  │    │    │                    └── CRC16
│  │    │  │  │    │    └── payload
│  │    │  │  │    └── 序號（小端序）
│  │    │  │  └── 命令碼（小端序）0x0050
│  │    │  └── 封包類型
│  │    └── 標頭 CRC8
│  └── 長度 << 3（小端序）0x00b0 >> 3 = 22 ✓
└── 魔術位元組
```

解析 12,026 個控制封包，**無一解析失敗**，結構確認無誤。

## 核心證據：序號恆為 0

```
-- 手機 → 飛機（控制）--
命令碼          筆數      序號行為
0x0050 搖桿控制  11,693    ★ 全部為 0 —— 無防重放
0x0025             230    ★ 全部為 0 —— 無防重放
0x0063              98    每筆遞增（1121–1218）
0x0030               2    固定 1119
```

**`0x0050` 是實際驅動飛行的搖桿指令。**
一次飛行送出 11,693 個，**序號全部是 0**。

對照之下，遙測方向（飛機 → 手機）的序號**是會遞增的**
（`0x1051` 遞增 6637–10303、`0x0063` 遞增 594–1846）。

→ **序號欄位在此協定中確實有作用，但控制方向刻意不使用。**
   這排除了「該欄位未實作」的可能，指向設計上就不做重放防護。

### 搖桿封包的酬載

```
t=0.000s  payload=00 042000290d0114 25 8700
t=0.020s  payload=00 042000290d0114 25 9c00
t=0.041s  payload=00 042000290d0114 25 b000
t=0.061s  payload=00 042000290d0114 25 c400
```

- 前段為打包後的搖桿軸值
- 末兩位元組每次遞增約 0x15（21），間隔 20 ms
  → **毫秒時間戳**，發送頻率 50 Hz

值得注意：時間戳是**明文且可預測**的，不構成防護。

## 安全性判讀

| 防護機制 | 狀態 |
|---|---|
| 加密 | ❌ 無，明文二進位 |
| 認證（token / 簽章 / 挑戰回應） | ❌ 無 |
| 序號防重放（控制方向） | ❌ 恆為 0 |
| 時間窗檢查 | ❌ 時間戳明文且可預測 |
| CRC8 / CRC16 | ⚠️ **完整性校驗，非認證**——演算法公開，可自行計算 |

**CRC 不是安全機制。** 它防的是傳輸錯誤，不是惡意偽造。

## MITM / 注入可行性評估

前提條件只有一個：**攻擊者位於 Tello 的 Wi-Fi 網段內**。

### 而這個前提的門檻是零：Tello 的 Wi-Fi 是開放網路

```
Network Id   SSID              Security type
1            TELLO-XXXXXX      open
```

（實測於 2026-08-18。SSID 尾碼已遮蔽，原值見 pcap，該檔不進版控。）

**無密碼、無 WPA。** 任何位於 Wi-Fi 訊號範圍內的裝置都可直接加入，
無需任何憑證、無需破解。

→ 本findings的攻擊前提**不構成實質障礙**。
   這與 F06 的結論一致，並將嚴重度定錨在 **High**。

達成後的攻擊步驟：

1. 被動擷取任一 `0x0050` 封包（明文，欄位可直接判讀）
2. 修改搖桿軸值，重算 CRC8 與 CRC16（公開演算法）
3. 送往 `192.168.10.1:8889`

**F06 的 TC-L1-06 已實測**：飛機會**接受**重放的封包
（該測試最初被誤判為「拒絕」，經 pcap 更正）。

本findings將該結論的適用範圍由 SDK 協定**擴展至 App 的原生協定**。

### 影像串流同樣無保護

`62512 → 7777` 的影像封包以 `be` 起始後接 H.264 NAL 資料，
**未加密**。F06 已成功抽出可播放的畫格（`TC-L1-05_stream.h264`）。

→ 同網段的任何人可被動側錄攝影機畫面。

## 附帶發現：飛行日誌正在被串流至 App

遙測方向出現 1,172 個 **`0x1051`** 封包。
於 DJI 協定中該命令碼為**飛行日誌資料**（`LOG_DATA_MSG`）。

其酬載含大量單一位元組的長串重複：

```
...6363636363636363636363636363...
...525252525252525252525252525252...
...a2a2a2a2a2a2a2a2a2a2a2a2a2a2...
```

**強加密不會產生這種長串重複。** 研判為 XOR 混淆或壓縮後的資料，
而非具備密碼學強度的保護。

→ **飛行紀錄確實被蒐集並傳給 App。** 這直通 RQ2。

> **本節的研判已於 F13 升級為確證。**
> 飛行後在 `files/droneLog/` 找到 `.DAT` 檔，內含 `DJI_LOG_V3` 標記，
> 且呈現與 `0x1051` 酬載**相同的單一位元組長串重複特徵**。
> 整條鏈為：飛機 → `0x1051` 封包 → App → `droneLog/*.DAT`。
> 至於是否事後上傳，F13 在未登入、5 分鐘的條件下**未觀測到**。

## 飛行期間的對外流量：零

以 10 秒為間隔、連續監測 2 分鐘（涵蓋整段飛行），
mitmproxy 的對外連線數**始終為 0**。

同時檢視 App 的 socket 表，僅有兩個 UDP 監聽埠（6525、7777），
**無任何 TCP 連線**。

→ 飛行期間 App 只與飛機通訊，未連線任何外部伺服器。

> ⚠️ 這**不代表**飛行資料不會外傳。
> `02-threat-model.md` 所述的時間差路徑——
> 飛行時無網路 → 資料暫存 → 之後連上網路才上傳——**尚未測試**。

## 階段二實測：飛行中注入搖桿封包**未觀測到任何效果**（2026-08-25）

本findings的核心推論是「任意來源可注入 `0x0050` 搖桿封包以操控飛機」。
該推論**已於實際飛行中直接測試，結果為否定**。

### 測試條件

| 項目 | 設定 |
|---|---|
| 飛機狀態 | **實際飛行中**，低空懸停，IMU 已校準無告警 |
| 官方 App | 正常連線並持續控制（50 Hz） |
| 飛手操作 | **手離開搖桿**，使 App 送出中位值，我方封包為唯一非中位輸入 |
| 注入內容 | `0x0050` 搖桿封包，單軸 +100（滿舵 660 的 15%） |
| 注入速率 | 約 11 Hz（受 `nc` 逐封包送出的程序開銷限制） |
| 記錄 | `tcpdump` 全程 + 螢幕錄影 180 秒 |

### 封包確實送達

```
我方送出總數      175 個（5 批 × 35）
長度              全部 22 bytes（格式正確）
來源埠            42121 / 53055 / 57752 / 51625 / 44580（每批不同）
```

**送達與格式皆無問題。**「沒反應」不是因為封包沒送出。

### 結果：飛機無任何可見反應

飛手全程目視，回報**四個軸向皆完全沒有反應**。

同時：

| 觀察 | 數值 |
|---|---|
| 飛機回給我方 5 個來源埠 | **全部 0 個封包** |
| 飛機回給 App（6525） | 4,349 個 |
| 我方注入期間 App 的控制流速率 | **49–51 Hz（完全正常）** |

**App 的工作階段未受任何干擾。**

### 兩個競爭解釋，本次無法區分

**(A) 協定具工作階段綁定**
飛機只接受已完成 `conn_req` 握手的來源。
此解釋與 **F15** 的觀察一致——App 連線中時，第二個 `conn_req` 被拒。

**(B) 注入幅度不足**
我方 11 Hz 對 App 的 50 Hz，封包被覆蓋約 80%；
15% 偏移經此折減後約等於 3%，可能低於可見閾值。

> ⚠️ **「飛機未回應我方來源埠」不足以判定。**
> 搖桿封包（`0x0050`）在正常運作下**本來就不會被 ACK**，
> 故零回應在「接受」與「忽略」兩種情形下皆會出現。
> 本findings不得以此作為 (A) 成立的證據。

### 對本findings的意義

**本findings原先的注入推論，在「擁有者已連線」的條件下未獲支持。**

須明確區分兩條路徑：

| 路徑 | 擁有者連線中時 | 證據 |
|---|---|---|
| 二進位 `conn_req` | ❌ 被拒 | F15 實測 |
| **二進位 `0x0050` 搖桿** | **❌ 未觀測到效果** | **本節實測** |
| **SDK 純文字 `command`** | **✅ 成功，且切斷擁有者影像** | **F16 實測** |

→ **同一台飛機的兩條控制路徑，安全模型並不一致。**
   二進位協定至少表現出工作階段的排他性；
   而 SDK 協定完全沒有任何綁定。
   **F16 才是實際可用的攻擊路徑。**

### 要如何確定

- [ ] 提高偏移至 300 以上（滿舵 45%）重測。若仍無反應，可大幅排除 (B)
- [ ] 提高注入速率至接近 50 Hz（現行 `nc` 逐封包的做法達不到）
- [ ] 於**無其他客戶端連線**時，先以 `conn_req` 建立我方工作階段，
      再自同一來源埠送出搖桿封包——可直接檢驗 (A)
      （**此測試需飛機在我方控制下飛行，風險高，須備妥降落手段**）

### 軸序對應已實測確認（TC-L1-13，2026-08-26）

原先四軸的語意係借用公開文件慣例，未經驗證。
以受控的操作序列擷取後，**對應關係已確立**。

#### 方法

飛機**置於地面、未起飛**（App 在連線狀態下仍持續送出 `0x0050`，
故不需飛行即可取得對照）。飛手依固定順序逐一推滿各方向，
每個動作維持約 3 秒，動作之間放開回中位以利切分。

#### 結果：八個區段與指定順序完全吻合

| 區段 | 指定動作 | 解出的軸 | 方向 | 極值 |
|---|---|---|---|---|
| 1 | 上升 | 軸3 | ＋ | 1684 |
| 2 | 下降 | 軸3 | － | 364 |
| 3 | 左轉 | 軸4 | － | 364 |
| 4 | 右轉 | 軸4 | ＋ | 1684 |
| 5 | 前進 | 軸2 | ＋ | 1684 |
| 6 | 後退 | 軸2 | － | 364 |
| 7 | 左移 | 軸1 | － | 364 |
| 8 | 右移 | 軸1 | ＋ | 1684 |

（`pcap:TC-L1-13-axis-calibration.pcap`，4,409 個搖桿封包 / 90 秒）

#### 確認的對應

```
軸1（bit 0–10）  = roll       ＋ 向右平移
軸2（bit 11–21） = pitch      ＋ 向前
軸3（bit 22–32） = throttle   ＋ 上升
軸4（bit 33–43） = yaw        ＋ 右轉

滿舵 = 中位 1024 ± 660，即 364 – 1684
```

與公開文件慣例（roll, pitch, throttle, yaw）**完全一致**。

#### 對階段二結果的意義

**「軸序搞錯」這個解釋因此被排除。**
階段二送出的 `+100` 確實作用於預期的軸，
且該值為滿舵 660 的 **15%**——經 App 50 Hz 覆蓋後實效約 3%。

→ 剩餘的兩個假設仍為 **(A) 工作階段綁定** 與 **(B) 幅度不足**。
   重測時可依實測的滿舵值精準指定比例（如 50% 舵量 = ±330）。



### 記錄限制

螢幕錄影受 `screenrecord` 的 180 秒上限，於 `23:56:25` 結束，
而 `ax3`（`23:56:32`）與 `ax4`（`23:56:41`）在其後送出，
**未被錄影涵蓋**。該兩批僅有 pcap 與飛手目視紀錄。

## 觀測邊界

- **未實際注入偽造的 `0x0050` 封包**（本findings撰寫時）。
  → **2026-08-25 部分更新**：**F15** 已實測證實飛機接受未經認證的連線
    （`conn_ack:` 於 87 ms 回覆），並主動推送飛行日誌與即時影像。
    因此「陌生來源可與飛機建立通訊」已由推論轉為實測。
    **但搖桿指令是否真的驅動飛機仍未實測**——F15 送出的是中位值，
    且飛機在地面未裝槳。下方原始敘述於此範圍內仍然成立。

- 本findings的注入可行性是
  「觀測到的協定屬性」加上「F06 在同一 UDP 埠的重放實測結果」所推得，
  **並非對 `0x0050` 本身的直接驗證**。
  實際注入測試具有失控撞機風險，需在空曠場地、有防護、並取得明確授權後進行。
- 僅一次飛行、一台機器、一個韌體版本（`01.01.0083`）
- ~~未驗證 Tello Wi-Fi 是否設有密碼~~ → **已於 2026-08-18 確認為 `open`**（見上）。
  惟本測試僅涵蓋**一台未曾設定過密碼的機器**；
  Tello 允許使用者自行設定 Wi-Fi 密碼，設定後的行為未測。
- `0x1051` 的酬載**仍未解出實際內容**。惟「是飛行日誌」一事已由 **F13** 證實
  （落地檔含 `DJI_LOG_V3` 標記且特徵相同），不再只是依協定慣例的研判
- 命令碼 `0x0025`、`0x0063`、`0x0030` 等的語意未確認
- 飛行期間飛控報 `ERROR CODE 29` / 感測器異常，
  不排除部分遙測行為與正常狀態有異
