## 摘要

以自有 Tello 實機驗證：**從連上 Wi-Fi 到取得完整控制權，
全程未發生任何認證、金鑰交換或裝置配對。**

前人已充分報告此問題，本findings為**複現以建立基準**，非新發現。
價值在於取得可重現的一手封包證據，並校正若干細節。

## 測試環境

```
無人機   Tello，SSID TELLO-<遮蔽>，BSSID 60:60:1f:<遮蔽>（OUI 60:60:1f 屬 DJI）
韌體     SDK 1.3 世代（sdk? 與 sn? 皆回 unknown command）
測試機   Windows 11，Killer BE1750x，單一無線介面
時間     2026-08-16 17:36–17:37
工具     tools/run_l1_capture.ps1 → dumpcap 4.6.8 + tello_probe.py
```

> ⚠️ SSID 與 BSSID 後綴為自有機器識別碼，報告中一律遮蔽。
> **SSID 後綴即 BSSID 後三個位元組** —— Tello 的 SSID 直接洩漏機身 MAC。

## TC-L1-01｜開放 AP，無密碼

`netsh wlan show networks mode=bssid`：

```
SSID 4 : TELLO-<遮蔽>
    Network type   : Infrastructure
    Authentication : Open
    Encryption     : None
    Radio type     : 802.11g       Band : 2.4 GHz
```

連線後：

```
State          : connected
Authentication : Open
Cipher         : None
```

**取得 IP `192.168.10.2`——由無人機的 DHCP server 主動配發。**
未輸入任何密碼、未提供任何憑證。

> 比預期更寬鬆：無人機不只開放關聯，還**主動跑 DHCP 配發位址**給任何連進來的裝置。

**判定：確認。**

## TC-L1-02｜無認證即成為控制端

### 決定性證據：連線後到第一個指令之間，零認證封包

pcap frame #1–#27 全部是**測試機自身的背景流量**
（IGMP、mDNS、SSDP、以及本機軟體嘗試對外連線）。
**沒有任何一個封包是與 192.168.10.1 的交握。**

第一個送往無人機的封包就是指令本身：

```
#28  2.93s  192.168.10.2 → 192.168.10.1  UDP 8889→8889  Len=7   "command"
#30  2.95s  192.168.10.1 → 192.168.10.2  UDP 8889→8889          "ok"
```

**送出 7 個位元組的明文字串 `command`，回 `ok`，即成為控制端。**
無挑戰回應、無金鑰交換、無配對、無序號、無時戳。

### 完整查詢序列（自 pcap 還原，13 送 / 14 收）

| # | 指令 | 回應 |
|---|---|---|
| 28→30 | `command` | `ok` |
| 34→35 | `sdk?` | `unknown command: sdk?` |
| 40→42 | `sn?` | `unknown command: sn?` |
| 45→46 | `battery?` | `85` |
| 50→53 | `wifi?` | `90` |
| 58→59 | `speed?` | `100.0` |
| 67→69 | `time?` | `0s` |
| 72→73 | `height?` | `0dm` |
| 79→81 | `temp?` | `88~90C` |
| 85→86 | `baro?` | `88.478081` |
| 95→96 | `tof?` | `65535mm` |
| 100→102 | `attitude?` | `pitch:-1;roll:0;yaw:0;` |
| 107→113 | `acceleration?` | `agx:-31.00;agy:17.00;agz:-1094.00;` |

**11/13 查詢取得有效資料**，全部明文 ASCII。
`sdk?` 與 `sn?` 不支援 → 此機為 **SDK 1.3 世代韌體**（`sdk?`/`sn?` 屬 SDK 2.0，
主要見於 Tello EDU）。這是本次校正的細節。

**判定：確認無認證、無裝置綁定。**

## TC-L1-04｜遙測可被動竊聽

**未送出任何指令即可接收**，來源 `192.168.10.1:8889` → `8890`：

```
pitch:-1;roll:0;yaw:0;vgx:0;vgy:0;vgz:-1;templ:88;temph:90;tof:6553;
h:0;bat:85;baro:88.17;time:0;agx:-28.00;agy:18.00;agz:-1099.00;
```

- **178 個遙測封包**（約 18 秒，≈10 Hz）
- **16 個欄位**：姿態三軸、速度三軸、加速度三軸、機身溫度上下限、
  ToF 測距、相對高度、**電量**、氣壓、飛行時間
- 明文 ASCII，無加密、無完整性保護

任何連上該 AP 的裝置都能持續取得無人機的即時狀態，**且完全不需要送出任何封包**。

**判定：確認純被動竊聽可行。**

## 附帶發現：另有兩條未經請求的二進位串流

除了文字 SDK 協定，無人機還**主動**送出 DJI 二進位協定封包：

```
#29   → 8889   cc 68 00 51 88 1a 00 0b 00 5a 00 a4 95
#51   → 8899   cc 68 00 51 88 1a 00 0c 00 5a 00 85 c2
#60   → 8899   cc 60 00 27 88 35 00 0d 00 00 a1 32
#78   → 8899   cc 68 00 51 88 1a 00 0e 00 5a 00 f3 fb
```

- 起始位元組 **`0xcc`** 為 DJI/Tello 二進位協定的 magic
- 第 8 個位元組逐次遞增（`0b`, `0c`, `0d`, `0e`, `0f`…）→ **序號欄位**
- 送往 **8899** 共 26 個封包；另有 1 個送往 8889（見下）

**意義**：無人機在 8889 上**同時支援文字 SDK 協定與二進位協定**，
且未經請求即主動推送。官方 App 使用的應是二進位協定——
這條路徑尚未分析，是後續可延伸的方向。

### 這個封包造成了一次資料汙染（已修正）

`#29` 的二進位封包在 `command` 的 `ok`（#30）**之前**抵達。
`tello_probe.py` 的第一次 `recvfrom` 將它當成 `command` 的回應，
導致其後**每個查詢都收到上一個指令的回應**，全序列平移一格。

初次判讀時據此得出錯誤對照（例如誤認 `sdk?` 回 `ok`、`battery?` 回 `unknown command`）。
**以 pcap 為準重新還原後才得到上表。**

> **教訓**：UDP 上的請求／回應配對不能假設一送一收。
> 腳本輸出只能當作輔助，**pcap 才是權威記錄**。
> 這也印證了 `10-tooling-spec.md` 要求「每個結論都要有證據指標」的必要性。

## 影響評估（誠實版本）

**攻擊者需要**：位於 Wi-Fi 涵蓋範圍內（2.4 GHz 802.11g，數十公尺）、
無人機已開機、一台任意電腦。無需事前接觸、無需憑證、無需特殊硬體。

**可造成**：完整控制權接管、即時遙測竊聽、（未測）影像竊聽與飛行指令注入。

**實務限制**：需物理接近且無人機開機。對個人休閒使用衝擊有限，
但對**教學現場多台同時飛行**的場景是真實問題——
誤連、互相干擾、惡作劇接管都可能發生，且使用者無從察覺。

**無緩解手段**：Tello 不提供設定 AP 密碼的選項，使用者無法自行改善。
