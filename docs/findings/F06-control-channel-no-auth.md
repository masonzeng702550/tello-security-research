## 摘要

以自有 Tello 實機驗證：**從連上 Wi-Fi 到取得完整控制權，
全程未發生任何認證、金鑰交換或裝置配對。**

前人已充分報告此問題，本findings為**複現以建立基準**，非新發現。
價值在於取得可重現的一手封包證據，並校正若干細節。

## TC-L1-02｜無認證即成為控制端

### 決定性證據：連線後到第一個指令之間，零認證封包

pcap frame #1–#27 全部是**測試機自身的背景流量**
（IGMP、mDNS、SSDP、以及本機軟體嘗試對外連線）。
**沒有任何一個封包是與 192.168.10.1 的交握。**

第一個送往無人機的封包就是指令本身：

```
#28  2.93s  192.168.10.2 → 192.168.10.1  UDP 8889→8889  Len=7   "command"
#30  2.95s  192.168.10.1 → 192.168.10.2  UDP 8889→8889          "ok"
```

**送出 7 個位元組的明文字串 `command`，回 `ok`，即成為控制端。**
無挑戰回應、無金鑰交換、無配對、無序號、無時戳。

|---|---|---|
| 28→30 | `command` | `ok` |
| 34→35 | `sdk?` | `unknown command: sdk?` |
| 40→42 | `sn?` | `unknown command: sn?` |
| 45→46 | `battery?` | `85` |
| 50→53 | `wifi?` | `90` |
| 58→59 | `speed?` | `100.0` |
| 67→69 | `time?` | `0s` |
| 72→73 | `height?` | `0dm` |

**11/13 查詢取得有效資料**，全部明文 ASCII。
`sdk?` 與 `sn?` 不支援 → 此機為 **SDK 1.3 世代韌體**（`sdk?`/`sn?` 屬 SDK 2.0，
主要見於 Tello EDU）。這是本次校正的細節。

**判定：確認無認證、無裝置綁定。**

## TC-L1-04｜遙測竊聽（附一則更正）

> ⚠️ **更正**：本節初稿寫「未送出任何指令即可接收」。**這是錯的。**
> 以第一次執行（探測腳本崩潰、未送出任何封包）作為對照組驗證後推翻：
>
> | | 是否送出 `command` | 無人機主動送出的封包 |
> |---|---|---|
> | 第一次執行（2.47 秒） | ❌ 未送 | **0 個** |
> | 第二次執行 | ✅ 於 2.930s | 218 個，首個遙測於 **3.050s**（+120 ms） |
>
> **無人機在收到 `command` 進入 SDK 模式之前，完全不廣播遙測。**
>
> 正確的表述是：**送出一個 7 位元組的明文封包之後**，即可持續被動接收遙測，
> 之後不需再送任何東西。門檻依然極低（無認證），但不是「零封包」。
>
> 觀測邊界：對照組的抓包視窗僅 2.47 秒。足以排除 10 Hz 的廣播，
> 但無法排除週期更長的行為。

進入 SDK 模式後，來源 `192.168.10.1:8889` → `8890`：

```
pitch:-1;roll:0;yaw:0;vgx:0;vgy:0;vgz:-1;templ:88;temph:90;tof:6553;
h:0;bat:85;baro:88.17;time:0;agx:-28.00;agy:18.00;agz:-1099.00;
```

- **178 個遙測封包**，時間跨度 17.80 秒 → **10.0 Hz**
  （間隔中位數 102.0 ms，範圍 44.6–152.0 ms）
- **16 個欄位**：姿態三軸、速度三軸、加速度三軸、機身溫度上下限、
  ToF 測距、相對高度、**電量**、氣壓、飛行時間
- 明文 ASCII，無加密、無完整性保護

任何連上該 AP 的裝置，**在送出一次 `command` 之後**，
即可持續取得無人機的即時狀態，其後不需再送出任何封包。

**判定：確認遙測明文外洩，門檻為單一無認證封包。**

### 指令回應延遲

13 組請求／回應：**中位數 27.0 ms**，範圍 5.0–54.1 ms。
反應快、無節流、無速率限制跡象。

## TC-L1-06｜指令重放與來源綁定（含一則判讀更正）

### 測試方法

以本機埠 8889 送出 `battery?` 並記下位元組序列，
再自**系統指派的另一個來源埠（61348）**原樣重送同一組位元組。

### 腳本初判：被拒絕 ❌ 錯誤

探測腳本回報重放逾時，初步判讀為「可能存在來源綁定」。

### pcap 覆核：實際上被接受 ✅

```
#325  21.28s  192.168.10.2:8889  → 192.168.10.1:8889   "battery?"
#326  21.34s  192.168.10.1:8889  → 192.168.10.2:8889   "94"

#334  21.74s  192.168.10.2:61348 → 192.168.10.1:8889   "battery?"   ← 重放
#336  21.79s  192.168.10.1:8889  → 192.168.10.2:8889   "94"         ← 回應送到 8889
```

**無人機接受並執行了來自任意來源埠的重放封包**，
只是把回應**寫死送回 8889**。腳本在 61348 上等待，因此誤判為拒絕。

### 判定

- **無重放保護** — 位元組完全相同的封包再次被接受，無序號／時戳／訊息驗證碼
- **無來源綁定** — 不檢查來源埠，任何埠送來的指令都執行
- 回應埠固定為 8889

**這比「被拒絕」嚴重得多。** 攻擊者可自任意來源埠注入指令；
若需要回應，另在 8889 監聽即可；
而**不需回應的指令（如 `takeoff`）連監聽都不必**。

### 更正紀錄

腳本已修正：重放測試改為**同時監聽原 socket（8889）與重放 socket**，
以 `select` 判斷回應實際抵達何處，可分辨
「拒絕執行」與「執行但回應送往他處」。

> **這是本次測試中 pcap 第二次推翻腳本的判讀**（第一次見下方的封包錯位）。
> 兩次都是同一類問題：**UDP 上不能從「沒收到回應」推論「對方沒處理」。**

## 附帶發現：DJI 二進位協定與文字協定並存

除了文字 SDK 協定，無人機**主動**推送 DJI 二進位協定封包，
分別送往 `8889` 與 `8899`。

### 封包結構（依已知的 Tello 二進位協定格式解析）

```
cc | len(13bit)<<3 | crc8 | pacType | cmdID(LE) | seq(LE) | payload | crc16
```

實例：
```
cc 68 00 51 88 1a 00 0b 00 5a 00 a4 95
│  └─┬──┘ │  │  └─┬─┘ └─┬─┘ └─┬─┘ └─┬─┘
│    │    │  │  cmdID  seq  payload crc16
│    │    │  pacType=0x88
│    │    crc8
│    len = 0x0068>>3 = 13 ✓
magic 0xCC
```

### 解析結果

| cmdID | 出現 | 長度 | 序號範圍 | payload | 研判 |
|---|---|---|---|---|---|
| `0x001A` | 18 | 13 | 11 → 36 | **90** | **Wi-Fi 訊號強度** |
| `0x0035` | 9 | 12 | 13 → 37 | 0 | 光線強度（待確認） |

**交叉驗證**：`0x001A` 的 payload 為 `90`，
與同一次測試中文字協定 `wifi?` 的回應 **`90`** 完全吻合
→ 可獨立確認此 cmdID 為 Wi-Fi 訊號強度。

`0x0035` 的識別僅依據社群逆向文件的對照表，**尚未獨立驗證**，標為研判。

**兩種訊息共用同一個全域遞增序號**（11、12、13…37 交錯出現），
非各自獨立計數。

### 意義

- 無人機在 `8889` 上**同時支援文字 SDK 協定與二進位協定**
- 官方 App 使用的應是二進位協定，本專案尚未分析該路徑
- 二進位協定**有序號欄位**（文字協定沒有），
  但序號是否被用於重放防護，需另行驗證（見 TC-L1-06）
- 有 CRC8／CRC16，但那是**錯誤偵測**不是**訊息驗證**——無金鑰，任何人都能算

### 這個協定造成了一次資料汙染（已修正）

`#29` 的二進位封包在 `command` 的 `ok`（#30）**之前**抵達。
`tello_probe.py` 的第一次 `recvfrom` 將它當成 `command` 的回應，
導致其後**每個查詢都收到上一個指令的回應**，全序列平移一格。

初次判讀時據此得出錯誤對照（例如誤認 `sdk?` 回 `ok`、`battery?` 回 `unknown command`）。
**以 pcap 為準重新還原後才得到上表。**

> **教訓**：UDP 上的請求／回應配對不能假設一送一收。
> 腳本輸出只能當作輔助，**pcap 才是權威記錄**。
> 這也印證了 `10-tooling-spec.md` 要求「每個結論都要有證據指標」的必要性。

## 影響評估（誠實版本）

**攻擊者需要**：位於 Wi-Fi 涵蓋範圍內（2.4 GHz 802.11g，數十公尺）、
無人機已開機、一台任意電腦。無需事前接觸、無需憑證、無需特殊硬體。

**可造成**：完整控制權接管、即時遙測竊聽、**即時影像竊聽（已驗證）**、自任意來源埠注入指令。

**實務限制**：需物理接近且無人機開機。對個人休閒使用衝擊有限，
但對**教學現場多台同時飛行**的場景是真實問題——
誤連、互相干擾、惡作劇接管都可能發生，且使用者無從察覺。

**無緩解手段**：Tello 不提供設定 AP 密碼的選項，使用者無法自行改善。
