# F15 — 未經任何認證即可取得無人機的即時影像與飛行日誌

| 欄位 | 內容 |
|---|---|
| 編號 | F15 |
| 層級 | L1 近場 Wi-Fi |
| 分類 | 認證缺失 / 機密性 |
| 嚴重度 | **High** |
| 受影響版本 | 韌體 `01.01.0083`（App 版本無關——本findings完全不經過 App） |
| 狀態 | **T2 — 直接實測，非推論** |
| 對應測試 | TC-L1-03 階段一 |
| 證據 | `pcap:TC-L1-03-stage1.pcap`、`pcap:TC-L1-03-stage1b.pcap` |
| 工具 | `tools/tello_inject.py` |

## 摘要

在**不使用官方 App、不提供任何憑證**的情況下，
以一個 `nc` 對無人機送出數個自行構造的封包，即取得：

- 飛機的 **`conn_ack:` 連線確認**（送出後 87 毫秒）
- **飛行日誌資料流**（`0x1050` LOG_HEADER 起始）
- **即時攝影機影像**，10.7 MB、含 39 個關鍵畫格，**已解碼為可視畫面**

F12 曾推論「任意來源可注入」，本findings以直接實測證實該前提，
並顯示影響不只是控制，**還包含資料外洩**。

> **範圍限定**：本攻擊成立於**無人機未被連線**時。
> 實測顯示已有客戶端連線時第二個 `conn_req` 會被拒（見下）。

## 攻擊前提：只有一項，且門檻為零

```
Network Id   SSID              Security type
1            TELLO-XXXXXX      open
```

**無密碼、無 WPA。** 任何位於 Wi-Fi 訊號範圍內的裝置都可直接加入。

## 實驗設計

刻意排除所有可能被質疑的干擾因素：

| 控制項 | 設定 |
|---|---|
| 官方 App | **完全未執行**（`force-stop` 並自最近任務移除） |
| 使用的工具 | Android 內建的 `/system/bin/nc`，無自訂程式 |
| 封包來源 | `tools/tello_inject.py` 自行構造 |
| 認證材料 | **無**——未提供帳號、密碼、配對碼或任何憑證 |
| 觀測方式 | `tcpdump` 於網卡層擷取，不依賴 `nc` 的回傳 |

> **為何不依賴 `nc` 的輸出**：`nc` 對 UDP 的接收行為不可靠（先前實測失敗）。
> 改以 `tcpdump` 作為觀察者、`nc` 僅作為發送器，
> 使「飛機是否回應」這一結論不受工具限制影響。

## 階段一之一：連線與飛行日誌

送出 **15 個封包**（3 個 `conn_req:`、12 個中位搖桿）。

### 飛機的回應

```
t=0.087s   636f6e6e5f61636b3a611e
           → "conn_ack:" + 0x1e61 (7777)
```

**飛機在 87 毫秒內確認了一個未經認證的連線。**

緊接著的第二個封包：

```
t=0.087s   cc 7008 09 88 5010 4204 c40b0000 27000000 03000000 2a000000 …
                        └ cmd=0x1050 (LOG_HEADER)
           酬載含 ASCII："BUILD May  7 2019 12:02:11"
```

該字串與 **F13** 在 `droneLog/*.DAT`（`DJI_LOG_V3`）中找到的完全相同。

→ **飛機一旦接受連線，立即開始推送飛行日誌。**

### 流量統計

| 方向 | 封包數 | 位元組 | 持續時間 |
|---|---|---|---|
| 我方送出 | 15 | — | 0–9.9 s |
| 飛機 → 遙測/日誌 | 2,109 | **89,306** | 0.087–170.5 s |
| 飛機 → 影像埠 | 3,915 | **5,418,821** | 至 14.2 s |

**送出 15 個封包，換回 5.5 MB 資料。**

### 影像埠是我方指定的

`conn_req:` 的酬載後兩個位元組即為「影像要送到哪個埠」：

```
conn_req:  63 6f 6e 6e 5f 72 65 71 3a  61 1e
           c  o  n  n  _  r  e  q  :   └─ 0x1e61 = 7777
```

飛機**照做**，將影像送往我方指定的 7777 埠。

## 階段一之二：取得可解碼的影像

第一輪的 5.4 MB 影像**無法解碼**——354 個 NAL 單元全為型別 1（P/B 畫格），
無 SPS、無 PPS、無 IDR。原因是未要求關鍵畫格。

自昨日的 App 流量中取出真實的 `VIDEO_START` 封包：

```
cc58007c60250000006c95      cmd=0x0025, seq=0, 酬載為空
```

> `tools/tello_inject.py` 可**逐位元組重現**此封包，
> 亦已對 `0x0030`、`0x0055`、`0x0062`、`0x0063`、`0x0064`
> 等六種命令碼與不同酬載長度全部驗證一致。

重送 `conn_req:` 後，每 0.5 秒送一次 `VIDEO_START`，共 40 次。

### 結果

```
影像封包 7,938 個 / 10,760,050 bytes

NAL 單元 884 個：
  型別 7  SPS 序列參數     39 個     ← 前一輪為 0
  型別 8  PPS 圖像參數     39 個     ← 前一輪為 0
  型別 5  IDR 關鍵畫格     39 個     ← 前一輪為 0
  型別 1  P/B 畫格        767 個
```

自第一個 SPS 起切出串流後以 `ffmpeg` 解碼：

```
codec_name = h264
width      = 960
height     = 720
pix_fmt    = yuv420p
avg_frame_rate = 25/1
```

**成功解出清晰可辨的室內畫面。**

> 該畫格為研究者自宅環境，依 `03-ethics-legal.md` 不納入版控、不對外提供。
> 原始 `.h264` 與 `.png` 僅存於工作區外的暫存目錄。

## 影響

攻擊者只需位於 Wi-Fi 訊號範圍內（Tello 標稱約 100 公尺），即可：

1. **即時窺看攝影機畫面** —— 無需任何認證，畫面品質為 960×720 / 25fps
2. **取得飛行日誌** —— 且該日誌的混淆已由 **F13** 完全求解
   （單位元組 XOR，金鑰存於酬載 `byte[2]`），**任何人都能立即解碼**
3. **與擁有者同時連線** —— 本次測試時 App 未執行，
   但協定未見任何「單一控制端」的限制機制（**未實測，見觀測邊界**）

且**擁有者不會收到任何提示**——飛機不會顯示「有第二個裝置連線」。

## 重要範圍限定：已有客戶端連線時，第二個連線被拒（2026-08-25 實測）

本findings的攻擊是在**官方 App 未執行**的條件下成立的。
為釐清真實情境中的嚴重度，另做一次對照測試。

### 測試設計

| 項目 | 設定 |
|---|---|
| 官方 App | **正常連線中**（影像串流運作，無告警） |
| 我方 `conn_req` | 自新的來源埠 `48706` 送出 |
| 宣告的影像埠 | **9999**（刻意不同於 App 的 7777，以便歸因） |
| 觀測 | `tcpdump`，涵蓋我方封包前後各數十秒 |

### 結果

```
t=12.389s   我方 48706 → 8889   conn_req:9999
t=12.442s   飛機 8889  → 6525   conn_ack:        ← 送給 App，不是我們

送到 9999 的封包        0 個
送到 48706 的封包       0 個
```

**飛機確實處理了我方封包**——整份擷取中僅有這一個 `conn_req`（我方送出），
而 53 毫秒後即出現 `conn_ack`，故該回應由我方觸發。

但飛機把 `conn_ack` 送往**既有客戶端的埠**，
且**未採用**我方宣告的影像埠，**未向我方來源埠送出任何資料**。

### App 完全未受干擾

| 通道 | 封包數 | 最大間隔 | 間隔發生時點 |
|---|---|---|---|
| App 控制 `6525→8889` | 2,273 | 21.9 ms | t=1.25s（**不在**我方封包時點） |
| 遙測 `8889→6525` | 720 | 227.9 ms | t=38.9s |
| 影像 `→7777` | 10,972 | 92.0 ms | t=38.9s |

我方封包時點（t=12.389s）前後的 11.5–14.0 秒區間內，
App 照常送出 124 個控制封包、收到 604 個影像封包。
測試後截圖顯示 App 畫面正常、影像即時、無任何告警。

→ **本次測試未觀測到任何干擾或阻斷效果。**

### 對本findings的範圍限定

**F15 的攻擊需要無人機處於未連線狀態。**

實務情境的差異：

| 情境 | 本findings的攻擊 |
|---|---|
| 無人機開機但擁有者尚未連線／已離線 | ✅ 成立 |
| 無人機開機且擁有者正在使用 | ❌ **連線建立階段被拒** |

無人機開機後至擁有者連上之前的空窗、
以及擁有者中途離線的期間，仍屬可攻擊窗口。

> **另一條路徑沒有這個限制。** **F16** 實測顯示，
> 同樣在擁有者連線中的狀態下，改送 SDK 的純文字指令 `command`
> **會成功**，且會切斷擁有者的影像連線。
> 故「已有客戶端時無法攻擊」的結論**僅適用於本節測試的 `conn_req` 路徑**。

> ⚠️ **本節的限定只涵蓋「連線建立」路徑。**
> 搖桿指令（`0x0050`）在既有連線存在時是否仍被接受，
> **本次未測試**——飛機在地面且未裝槳，
> 即使接受指令也無從觀測。此問題只能由階段二（實際飛行）回答，
> 且它才是「飛行中劫持」是否成立的關鍵。

## ⚠️ 觀測邊界

- **未實測搖桿指令是否真的驅動飛機。** 本次飛機在地面、未裝螺旋槳、未解鎖。
  送出的 12 個搖桿封包為中位值（等同不操作）。
  **「可注入控制指令」仍是推論，尚待階段二。**
- **未測試與 App 同時連線的情形。** 本次 App 未執行。
  兩個控制端並存時的行為（誰優先、是否互斥）未知。
- 僅一台機器、一個韌體版本（`01.01.0083`）
- **未驗證 Tello 設定 Wi-Fi 密碼後**是否仍可如此連線
- 飛行日誌的**實際欄位內容未解析**，僅確認其存在與格式標記
- 本次飛機處於 `ERROR CODE 29` 感測器告警狀態，
  不排除部分行為與正常狀態有異
